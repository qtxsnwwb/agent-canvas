# agent-canvas 使用手册

> 这里是完整的参考说明。想快速上手请看[项目首页](../README.md)。

agent-canvas 是一个本地服务：它读取 Claude Code 的 transcript 文件、OpenAI Codex 的会话文件和 Cursor 的本地数据库，以及 Gemini CLI、Grok、GitHub Copilot CLI、DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作、Qwen Code 的会话文件（这八个未经真实数据核对），并接收 hook 事件，在固定的本地网址上用网页展示每个会话正在做什么。各种工具的会话用同一套页面展示（见下文“Codex”“Cursor”“Gemini CLI、Grok、Copilot CLI”“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”“Qwen Code”）。
每个会话显示为一张实时更新的画布。默认的“概览”视角只画骨架（每个轮次一张卡片，下面挂它派出的子代理），选中一个轮次或子代理，它的执行过程在下方以瀑布图列出。另有逐步、拓扑、因果、复盘四个视角（见下文“画布”）。首页可以检索会话，诊断页给出服务和 hooks 的运行情况。

## 从 claude-canvas 升级

这个项目原名 claude-canvas，接入 Codex 和 Cursor 之后改名为 Agent Canvas。新版本**不认任何旧名字**，从旧版本升级时需要手动做一次：

1. 停掉旧服务。
2. 数据目录改名：把 `~/.claude-canvas` 改成 `~/.agent-canvas`（不改的话新版本会从空库开始，重新导入全部会话）。
3. 环境变量改名：`CLAUDE_CANVAS_*` 一律改成 `AGENT_CANVAS_*`，名字的其余部分不变。
4. 如果移动或改名了项目文件夹：Codex 和 Cursor 的 hooks 里写的是 `cli.js` 的绝对路径，需要在旧位置先 `hooks uninstall --codex` / `--cursor`，再在新位置重新安装（Codex 还要重新确认信任）。Claude Code 的 hooks 指向的是端口地址，不受影响。
5. 浏览器里记住的首页筛选和精简模式会回到默认值，重新选一次即可。

## 环境要求

- Node ≥ 22（读取 DeepSeek Harness 的会话需要 Node 22.15 或更高，见“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”）
- 从源码运行时还需要 pnpm（可选：没有全局安装时用 `npx --yes pnpm@10` 代替 `pnpm`）

## 安装与启动

### 从 npm 安装（推荐）

```
npx @qtxsnwwb/agent-canvas                 # 临时运行，不安装
npm install -g @qtxsnwwb/agent-canvas      # 或者全局安装，之后用 agent-canvas 命令
agent-canvas
```

- 不带参数等同于 `start`；`agent-canvas --port 4400` 换端口；`agent-canvas --version` 打印版本；`agent-canvas --help` 打印用法。
- 下文里的 `node packages/server/dist/cli.js <命令>` 是从源码运行时的写法；从 npm 安装后一律换成 `agent-canvas <命令>`（或 `npx @qtxsnwwb/agent-canvas <命令>`）。
- **用 `npx` 临时运行时不能安装 Codex 和 Cursor 的 hooks**：这两种 hooks 里写的是程序的绝对路径，`npx` 的缓存位置随时可能变。这时 `hooks install --codex` / `--cursor` 会拒绝并提示先全局安装。Claude Code 的 hooks 指向端口地址，不受影响。
- 全局安装后升级（`npm install -g @qtxsnwwb/agent-canvas@latest`）路径不变，hooks 不需要重装。

### 从源码运行

已安装 pnpm：

```
pnpm install
pnpm build
pnpm start
```

未安装 pnpm：

```
npx --yes pnpm@10 install
npx --yes pnpm@10 build
npx --yes pnpm@10 start
```

启动后终端会打印：

```
agent-canvas listening on http://127.0.0.1:4317
```

在浏览器打开 <http://127.0.0.1:4317> 即可。按 Ctrl+C（SIGINT）停止服务。

换端口：`pnpm start --port 4400`（或直接 `node packages/server/dist/cli.js start --port 4400`），打印的地址会随之变化。

首次启动会导入 `~/.claude/projects` 下全部已有的 transcript；历史很多时需要一段时间，导入在后台进行，页面在此期间已可使用（`GET /api/diagnostics` 的 `importing` 为 `true`，诊断页上显示“正在导入：是”）。在一份真实数据上测得（340 MB、612 个文件）：导入约 2 分钟，导入完成后数据库约为 transcript 总量的 1.6 倍；导入期间 WAL 文件会临时增长到 transcript 总量的数倍，之后收缩到 64 MB 以内，请为数据目录预留空间。之后服务会持续监视 transcript 的变化。

同一个数据目录只能运行一个服务：启动时会创建锁文件 `<数据目录>/agent-canvas.lock`（记录 pid 和启动时间）。若已有服务在运行，第二次 `start` 会打印 `agent-canvas is already running with this data directory (pid N); lock file: …` 并以退出码 1 退出。上一次进程异常退出留下的锁会被自动接管。

升级 agent-canvas 后，如果推导规则的版本变了（或上次重建被中断），`start` 会在开始监听前自动重建派生数据，先打印 `agent-canvas rebuilding derived data (reason: …)`，再打印正常的监听地址。2026-11-10 在一份真实数据上测得：升级时有 14 个会话被自动重新推导（这是一次测量，不是保证）。

## 首页与检索

首页按项目列出会话，项目内按最近活动时间排序。

- 项目名：取该项目下会话的工作目录中，编码后（非字母数字字符换成 `-`）与项目目录名相同的那个；找不到时显示项目目录名本身。
- 会话标题按以下优先级取第一个有的：自定义标题（`/rename` 等写入的 custom title）> agent 名称 > hook 提供的标题 > 第一条提示（去掉首尾空白、换行折成空格，取前 60 个字符）。

顶部的检索框：

结果分两组：

- **会话**：会话标题、会话 id、分支、工作目录，以及每条主线程提示的前 200 个字符。每个会话最多列出 3 处命中，点结果打开该会话。
- **内容**：会话里面的文字——提示、回复、思考（有文本的那部分）、工具名和它的输入（命令、参数）、工具输出的前 8 KB、系统节点的文字；子代理内部的步骤同样能搜到。每个会话最多列出 5 处命中，最多 50 个会话，同一会话的命中归在一起；点一处命中会打开那个会话并选中、定位到那一步（地址是 `#/s/<会话 id>/n/<节点 id>`，可以收藏或分享给自己）。

规则：

- 至少输入 2 个字符才开始检索；查询最多取前 200 个字符。
- 按字面匹配：不支持通配符、正则或布尔语法，引号、星号、括号都当普通字符；只有 ASCII 字母不区分大小写（`É` 和 `é` 视为不同字符）。命中处在结果里高亮。
- **恰好两个字符的词**（比如两个汉字）索引帮不上忙，只在最近 30 天有活动的会话的提示和回复里找，页面上会注明。想搜得全，多打一个字。
- 工具输出只索引前 8 KB：很长的输出里靠后的内容搜不到（要找的报错、路径通常在开头）。
- 结果很多时只显示一部分，页面会提示“试试更长的词”。
- 首页按来源筛选时，内容命中也只列该来源的。
- 页面提示“索引正在重建，结果可能不全”时，说明检索索引还在后台建（升级后第一次启动、或做过全量重建之后会这样，本机数据量下几分钟），建好之前只能搜到已经建好的部分。进度在诊断页的“数据库”一栏。

## 画布

### 概览（默认）

- 画布上每个轮次是一张卡片：提示内容、工具调用次数、历时、失败数；正在进行的轮次带呼吸动效，并显示“正在执行 <工具名>”。轮次派出的子代理是挂在卡片下面的节点，子代理里再派出的子代理挂在它下面。
- 画布下方是“执行过程”面板（瀑布图）：每一步一行，按开始时间排列，右侧横条画在同一条时间轴上，长度就是耗时，并行的步骤在时间上重叠。没有时长的步骤（提示、回复）画成一个菱形标记。
  - 没有选中任何东西时，面板跟随最新的轮次；点画布上的轮次卡片或子代理节点，面板改为列出它的步骤；点画布空白处回到跟随最新。
  - 点一行，在右侧抽屉里看这一步的完整入参和输出；子代理那一行上的“内部步骤”切到那个子代理。
  - 打开一步之后，面板里导致这一步的那些步骤（沿连线往回直到本轮提示，子代理里的步骤会接到派出它的那一步）左侧带标记，其余变淡；其中这一步的“直接依据”（往回遇到的最近一段思考和回复，子代理里则是它的任务提示）用橙色底标出。抽屉顶部的“推理链”按时间顺序列出链上的思考和回复，直接依据带标签，点一行跳到那一步。
  - 会话已经停下（空闲、结束、长时间无活动）时，没有结束的步骤不再随时间变长，面板标题显示“有步骤未结束”。
  - 窗口较窄（不足 1100 像素）时，抽屉只盖住上面的画布，面板保持整行宽度。
  - 有步骤在执行时，面板每秒更新一次；滚动条在底部时会跟着新步骤往下走。
  - “精简”时面板不列没有内容的思考和普通系统记录，“完整”时全部列出。
- 点面板右上角的 × 关闭面板；再点任意轮次或子代理重新打开。

### 逐步及其他视角

以下说明针对把每一步都画成画布节点的“逐步”视角，以及在它基础上的拓扑、因果、复盘。

- 网格式自动布局：每个轮次（一次提示及其后的回复、工具调用）排成一块；轮次按时间从左到右排，一行排满（约四张大纲卡片的宽度）就换行，行与行之间有一条回折线把上一行末尾连到下一行开头。轮次内部的步骤自上而下排，超过约一屏高时折成并排的几列（分叉到汇合的一段不拆开）；并行的工具调用左右排开。画布不会随着会话变长而一直往下延伸。
- 状态颜色：执行中为蓝色、等待权限确认为橙色（两者带呼吸动效），成功为绿色、失败为红色、被拒绝为深红色；没有状态的节点按类型着色（提示为紫色）。
- 默认是“精简”显示（会话页右上角的“精简 / 完整”开关，选择会记在这个浏览器里）：
  - 没有记录内容的思考节点不单独画，它的耗时显示在后面那个节点上（“思考 3.2s”，不足 1 秒不显示）；有内容的思考节点、以及正在进行的最后一个思考节点照常显示。
  - 系统节点不画，上下文压缩和用户中断除外。
  - 同一个轮次、同一条线程里连续 3 次及以上成功的同一种工具调用（先后发生的，或同一步并行发出的）合并成一个节点，如“Read ×5”；点它展开成各次调用，之后保持展开。失败、被拒绝、仍在执行的调用不合并。停止跟随期间不会形成新的合并节点。
  - 切到“完整”则每条记录都画成一个节点。在一组真实数据上，精简后节点数从 24,068 降到 11,696。
- 默认只展开最后 3 个轮次，更早的轮次各折叠成一个摘要节点（节点数、工具调用数、耗时、失败数）。点摘要节点（或其中的“展开”）展开该轮次，点轮次标题栏上的“折叠”把它折回去。
- 一个轮次很长时（超过 60 个节点），只显示它的提示和最后 40 个节点，中间的折叠成“更早的 N 个节点”；点其中的“展开全部”显示整个轮次。仍在执行或等待权限确认的节点不会被折叠进去。
- 画布会跟随最新的节点，直到你平移、缩放或展开 / 折叠了什么；不跟随时右下角出现“回到最新”，点它恢复跟随。停止跟随后，新轮次到来时也不会自动折叠已展开的轮次，以免内容在你阅读时移动。
- 点一个节点（或用 Tab 聚焦后按 Enter / 空格）在右侧抽屉里查看它的完整内容：文本、入参、输出和原始记录；按 Esc 或 × 关闭。
- 子代理默认收起为单个节点（带内部节点数）；点节点上的“展开”把它展开成一个容器，里面按同样的规则排布它的内部节点，再点“收起”收回去。子代理里派发的子代理也能在容器里继续展开（嵌套）。一个子代理的内部节点很多时（超过 60 个），和长轮次一样只显示它的第一个节点和最后 40 个，中间的折叠成“更早的 N 个节点”，点“展开全部”显示全部。
- 信息栏右侧可以切换视角：
  - 逐步：全部节点，子代理可以展开。
  - 拓扑：隐藏思考和回复节点，只看提示、工具调用和子代理（子代理一律收起），被隐藏节点两侧的连线接到一起，链路不断开。
  - 因果：节点和逐步视角相同，思考节点放大显示它的内容（没有记录内容时显示时长）。选中一个节点后，从它沿连线往上直到本轮提示的那条链被高亮，其余变暗；抽屉里的“推理链”按时间顺序列出链上的思考和回复，点其中一行选中那个节点。链被折叠截断时，抽屉里会提示“更早的部分已折叠”，点“展开”展开截断它的轮次或节点。在因果视角选中节点会停止跟随，链上的内容不会在阅读时被折叠走。
  - 复盘：把会话回放到过去的某一时刻，见下一节。
- 2026-11-10 在一份真实数据上测得：最大的会话（约 7,500 个节点）从打开到画出画布约 1 秒（测量值，不是保证）。

### 复盘

复盘视角在画布下方显示一条时间轴，范围从会话最早的节点开始，到最晚的节点开始或结束为止：

- 播放 / 暂停，倍速 1× / 10× / 60×；播放到末尾自动停止，在末尾再点播放从头开始。“回到末尾”直接跳到最后。
- 拖动滑块选择时刻；滑块上方每个轮次一个刻度，点刻度跳到该轮次开始。滑块获得焦点时，PageUp / PageDown 跳到上一个 / 下一个轮次（刻度本身不参与 Tab 切换）。
- 时间轴显示当前时刻（回放范围跨了日期时带上 `MM-DD`）和“第 N / M 轮”。
- 画布只显示该时刻及之前出现的节点，之后的隐藏；在该时刻还在执行中的工具显示为执行中。
- 工具和子代理节点下方多一行耗时和 token（输入 / 输出），回复节点只显示 token；时间轴右侧是到该时刻为止的节点数和 token 合计，同一条消息拆成的多个节点只计一次。
- 历史会话里工具的耗时由开始和结束时间推算（hook 提供了 `duration_ms` 时用 hook 的值）。

### 时间线

会话页右上角的视角切换最后一项是“时间线”，用来回答“这个会话的时间都花在哪个子代理上了”。切过去，画布换成下面的视图；“执行过程”面板还在。

- 每条线程一行：第一行是主线，子代理缩进在派出它的那条线程下面。所有横条画在同一条时间轴上，下方是时刻刻度。
- 横条里颜色浅的部分，是这条线程在等它自己派出的子代理（主线上浅色的部分就是在等）。一个子代理被派出过好几次时，横条分成几段，每次派出一段，两段之间它没在干活的空闲不画。
- 每个子代理一行有两个数字：
  - **等待**（主线等它的时间）：每一刻只算给一条线程。主线在等的那一刻，同时在等几个子代理时，算给最后结束的那一个（它才是真正拖住主线的）；它自己又在等它派出的子代理时，再往下算，算给最深的那一个。所以所有子代理的等待加上主线自己干活的时间，正好等于总用时，不会重复。
  - **各自用时**：它自己每次被派出后干了多久，按每次派出分别算再相加。并行的子代理各算各的，加起来可以超过总用时。
  - 主线那一行显示“自己”（主线自己干活的时间）和“等”（其余的时间）。
- 同一层的子代理默认按“等待”从多到少排，等待最多的标“最长”；可以切成“开始时间”排。排序只在同一层之间进行。
- 鼠标移到一行上，提示里有：派出它的那一步、开始和结束时间（或“进行中”）、步骤数、token，被派出不止一次时还有派出几次。步骤数跟着“精简 / 完整”开关。屏幕阅读器能读到这些内容；主线横条可以用方向键选轮、回车打开；触屏看不到。
- 点子代理那一行，下方“执行过程”面板切到它的步骤；点主线横条上的某一处，面板切到那一刻所在的轮次。
- 总用时只算轮次之内的时间：从每一轮的提问开始，到这一轮主线最后一个不是派出的步骤结束，或这一轮里主线在等子代理的那段结束，取较晚的；两轮重叠的部分只算一次，两轮之间用户思考、离开的时间不算。
- 轮次结束之后还在后台跑的子代理：横条照常画，算进它自己的“各自用时”，不算进任何人的等待（那时没有人在等它）。
- 时间轴上两轮之间超过 5 分钟、而且这段时间里没有任何子代理在干活的空白，压缩成一个 `//` 断开记号；有子代理在跑的空白不压缩。
- 没有子代理的会话只画主线，并写明“这个会话没有派出子代理”。

怎么判断“主线在等谁”：

- 一般的来源（Claude Code、Gemini、Qwen Code、WorkBuddy、CodeBuddy 等）：派出子代理之后，主线一直算在等它，直到主线开始了这条消息之外的下一步（包括又派出另一个子代理）。后台派出的子代理，在主线还在干活时不算等待。主线停下来闲着、而它还在跑的那段，算在等它：比如主线说“已经派出去了，做完再汇报”就停下，直到它结束的通知把主线叫醒，中间这段就是在等它。这不会把一轮拉长：轮次结束之后的时间，仍然不算任何人的等待。页面看不出“后台”这个标记，只能看主线有没有接着干活，所以后台派出之后、主线开始下一步之前的那几秒（通常是模型的响应时间）也算在等。
- Codex：派出子代理和给它追加任务都不算等；只有 `wait_agent` 那一步算在等，主线的和子代理自己的都算。等的是它参数里点名的子代理；点名的子代理都不在这条线程所在的那一棵派出关系里（比如找不到派出它的一步的子代理）时，不算在等任何人。点名读不出来时，算给当时在干活的、这条线程派出的子代理，有几个就算给最后结束的那一个。轮次结束之后还在跑的后台工作，画出来、算进它的各自用时，但不算进任何人的等待。
- 豆包：同一轮里所有步骤记的是同一个时刻，没有可用的时间，时间线只显示“这个来源没有记录每一步的时间，无法生成时间线”。
- 其他来源的会话，如果步骤一个可读的时间都没有，时间线只显示“这个会话的步骤没有可读的时间，无法生成时间线”。
- 派出的那一步没有记下是哪个子代理（Copilot 的并行子代理，以及 Qwen、DeepSeek、WorkBuddy 里没配上的）：画成一行“未配上”，它承接这一步的等待，各自用时按这一步自己的起止。找不到派出它的那一步的子代理，和主线派出的子代理排在同一层，鼠标提示里写着“找不到派出它的一步”，等待为 0。

和概览的差别：

- 概览里轮次卡片的“历时”算到这一轮最后一步的开始，时间线算到最后一步的结束，所以两个数会差一点。
- 会话很大（一万个节点以上）时，时间线在后台线程里计算，数字稍后出现；导出的 HTML 文件里也有时间线，用导出时的快照，在页面主线程里算，进行中的横条不再变长。

限制：

- Grok 把每条记录接在前一条后面，没有“同一条消息”的标记，所以和派出同时发出的调用会被当成主线继续干活：调用执行的那段算主线自己的，调用结束后主线闲着的时间照常算在等。
- 鼠标提示在触屏上看不到。
- 上面这些规则按自造的数据测过，没有用真实会话核对过。

## Codex

- 服务启动时会自动读取 `~/.codex/sessions` 下的 Codex 会话文件（Codex 桌面应用和 CLI 写的都是这里），并持续监视。目录不存在时跳过，不报错。
- 用环境变量 `AGENT_CANVAS_CODEX_DIR` 指定别的目录；设为空字符串表示不读取 Codex。
- 会话标题取自 `~/.codex/session_index.jsonl`（Codex 给会话起的名字），没有时取第一条提示。
- 同一个工作目录下的 Claude Code 会话和 Codex 会话属于同一个项目。
- 首页会话卡片、检索结果和会话页信息栏上标明来源（Claude Code 或 Codex）。两种来源都有的项目，项目卡片上有两个小标记。
- 有 Codex 会话时，首页项目列表上方出现“全部 / Claude Code / Codex”筛选，选择记在这个浏览器里。筛选后没有该来源会话的项目不显示；地址里指定的项目即使被筛掉也照常显示。服务给出的项目会话数不分来源，所以筛选时，同时有两种来源的项目不显示会话数，顶部只在数字准确时显示会话总数和进行中的数量。
- Codex 的子代理是单独的线程，显示为派出它的那一步下面的子代理，展开后是它内部的步骤。

### Codex hooks（可选）

不装 hooks 也能用：服务靠监视会话文件得到 Codex 会话，延迟几秒。装上后多了两样，接近实时（1 秒内）：会话状态的变化（开始运行、结束、已退出），以及等待权限确认（会话显示“等待权限确认”，该轮次里最新一个还在执行的工具节点也显示等待确认）。hooks 不新建节点，也不决定节点的结果：步骤一律来自会话文件，所以工具节点并不会因为装了 hooks 而更早出现；除了等待权限确认期间那个临时的“等待确认”标记，有没有 hooks 画出来的图完全一样。

Codex 的 hook 只能运行命令，不能直接发 HTTP，所以 agent-canvas 提供一个转发命令：`node <agent-canvas>/packages/server/dist/cli.js hook-forward --origin codex --port 4317`。它从标准输入读 Codex 给的 JSON，原样发给本机服务的 `/hooks?origin=codex`，然后退出。

安装与移除（流程和 Claude Code 的 hooks 一样：先列出改动、确认、备份、只追加）：

```bash
node packages/server/dist/cli.js hooks install --codex      # 写入 ~/.codex/hooks.json（不存在时新建）
node packages/server/dist/cli.js hooks uninstall --codex    # 只移除本安装、本端口的那几条
```

- 写入 11 个事件：`SessionStart`、`SessionEnd`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`SubagentStart`、`SubagentStop`、`Stop`、`PostCompact`、`Interrupt`。每条都是 `async: true`（后台运行，不改变 Codex 的结果），`command` 和 `commandWindows` 都写，用绝对路径指向当前的 `node` 和这份 `cli.js`。超时：`SessionEnd`、`Interrupt` 是 3 秒（Codex 对这两个事件最多允许 3 秒），其余 5 秒。
- Windows 上的命令（`commandWindows`）尽量写成不带引号的形式，例如 `C:\PROGRA~1\nodejs\node.exe C:\Users\me\AppData\Roaming\npm\node_modules\@qtxsnwwb\agent-canvas\dist\cli.js hook-forward --origin codex --port 4317`。原因：Codex 在 Windows 上用 PowerShell（`powershell -NoProfile -Command <命令>`）执行 hook 命令，只有本地环境没准备好时才退回用 `cmd /C`；以带引号的路径开头的命令在 PowerShell 里是语法错误，`& "…"` 的写法在 cmd 里又是语法错误，只有不带引号的写法两边都能运行。路径只由字母、数字和 `_ . : \ / ~ -`（以及不在开头的 `@`，例如全局安装路径里的 `\@qtxsnwwb`）组成时原样写；含其他字符（空格、括号、`&`、非英文字符等）时换成 Windows 的 8.3 短路径。短路径在安装时向系统查询（`cmd.exe` 的 `%~s`），只有它同样只含这些字符、并且确认指向同一个文件时才用。
- 写不成不带引号的形式时，改用 PowerShell 的调用形式 `& "<node>" "<cli.js>" hook-forward …`（能写成不带引号的那个路径照样不带引号），安装时会多打印一行说明。这种形式在 PowerShell 下能运行，但在 Codex 退回用 cmd 时不能运行。常见情形：路径所在的磁盘关闭了 8.3 短名（系统盘以外的盘常见），或者路径里有非英文字符（例如中文用户名 `C:\Users\张三\…`），而短名里仍有这些字符、查到的结果用不上。路径里有 `"`、`` ` ``、`$` 或中文引号 `“ ” „`、又没有可用的短路径时拒绝安装（这些字符在 PowerShell 的双引号里会被解释），请把 node 或 agent-canvas 装到别的路径。
- 已装好的不带引号的条目，只要命令里的路径仍指向当前的 node 和 `cli.js`，重装时就不会改写（即使这次没查到短路径），以免无谓地要求重新确认信任。
- **从旧版本升级的 Windows 用户**：旧版本写的 Windows 命令（`"<node>" "<cli.js>" …`，以带引号的路径开头）在 PowerShell 里无法运行，所以在通常情况（Codex 用 PowerShell 执行）下这些 hooks 从没转发过事件（只有 Codex 退回用 cmd 时能运行）。升级后请再运行一次 `hooks install --codex`：它认得出旧版本写的条目，把 11 条都原位换成新写法，然后需要在 Codex 里重新确认信任。
- 选项和 Claude Code 的一样：`--port <n>`、`--yes`（非交互终端必须加）、`--settings <file>`（写别的文件）；环境变量 `AGENT_CANVAS_CODEX_HOOKS_FILE` 改默认路径。`~/.codex` 目录不存在时视为没装 Codex，不做任何改动。
- **装完要在 Codex 里确认信任这些 hooks 才会运行**：桌面应用在“设置 → Hooks”，CLI 里输入 `/hooks`。没确认时 agent-canvas 只靠会话文件工作，诊断页的 Codex 一栏会显示“尚未收到 Codex 的 hook”。
- Codex 的信任绑定在 hook 的内容和位置上（按 hooks.json 路径、事件、第几组、组里第几个记录）。移动或升级 agent-canvas 后命令里的路径会变：先 `hooks uninstall --codex`（在旧位置运行）或手动删掉旧的几条，再在新位置 `hooks install --codex`，并重新确认信任。
- 换了 node（例如用 nvm / fnm 升级后旧路径失效），或命令是旧版本的写法时，再运行一次 `hooks install --codex`：它认得出本安装的旧条目、说明它们已过期，并在同一次写入里原位换成当前的命令（同一个事件、同一组、组里同一个位置，所以同一文件里别人的 hooks 位置不变、信任不受影响；替换后的条目要在 Codex 里重新确认信任）。新装的事件仍然加在末尾。判断“本安装的条目”时按命令解析出 `cli.js` 的路径比较（Windows 上不分大小写，长路径和短路径都认），端口写成 `--port 4317`、`--port=4317` 或不写（默认 4317）都认。
- 卸载时删掉我们的条目，不留空组（Codex 是否接受空组未知）。如果同一事件里排在我们后面还有别人的 hooks，它们的位置会前移，Codex 会把它们当成改动过的、需要重新确认；卸载时会打印一行列出这些事件。
- 失败行为：转发命令永远以退出码 0 结束、不输出任何内容、不读写文件；服务没启动时立刻退出（连接被拒），服务不回应时 1 秒后放弃。Codex 的行为不受影响。每个 hook 事件会启动一次 node（本机实测转发命令从启动到退出约 0.25 秒，和空跑 `node` 差不多）。大多数事件（包括 `Interrupt`）因为是 `async` 在后台运行，不拖慢 Codex；但 `SessionEnd` 即使写了 `async: true`，Codex 也同步运行它，所以退出时会多等一次转发：通常约 0.25 秒，服务卡住时最多约 1.3 秒（转发命令自己的 1 秒上限加启动），无论如何不超过 3 秒的超时。
- hooks 只给出会话状态和权限等待，节点、状态、开始和结束时间都以会话文件为准。会话状态由会话文件里主线程的轮次和 hook 留下的标记一起算出，与两者到达的先后无关：子代理线程的 hook（带 `agent_id`，或它的轮次已在会话文件里归到子线程）不会把已经结束的会话改回运行中；同一轮次在 `Stop` 之后又收到 `UserPromptSubmit` 或 `PermissionRequest`，说明这一轮还在继续，会重新算作运行中；`Stop` 先于或晚于会话文件里的轮次结束到达，结果一样。

已知限制：

- 思考内容：Codex 的思考正文是加密的，只有摘要，而且摘要多数为空。Codex 会话的“因果”视角主要靠回复文本。
- token：Codex 的用量按“每次模型响应一条记录”归到这次响应产生的第一个节点上；Cursor 没有 token 数据。
- 已归档会话（`~/.codex/archived_sessions`）不导入。归档一个会话后，它在这里显示为“源文件已删除”，已采集的内容仍可看。
- Codex 的会话文件格式不是稳定接口，升级 Codex 后可能出现未识别的记录，可在诊断页查看。
- Codex 自己发起的审批复核线程（不是由某次工具调用派出的）不显示。
- Codex hooks 需要使用者在 Codex 里手动确认信任，改动或重新安装后要再确认一次；没确认时只靠会话文件，延迟几秒。
- Codex hooks 的核对状态（对照 Codex 源码 openai/codex `main` 的提交 `75fc67e`，约 rust-v0.171；还没有用真实的 Codex 运行核对）：
  - 已对照源码确认：`~/.codex/hooks.json` 的格式和 11 个事件名；hooks 默认开启（功能开关 `hooks`，只有 `[features] hooks = false` 才关）；`timeout` 的单位是秒，`SessionEnd` / `Interrupt` 最多 3 秒；`async: true` 的 hook 在后台运行；各事件的字段（`session_id`、`transcript_path`、`cwd`、`hook_event_name`、`model`，工具事件的 `tool_name` / `tool_input` / `tool_use_id`，`PermissionRequest` 不带 `tool_use_id`）；`turn_id` 和会话文件里轮次结束记录用的是同一个 id（轮次开始记录的写入处没有找到，按同一来源推断，最终仍要真实运行核对）；子代理的 hook 带 `agent_id`（子代理自己的线程 id）和 `agent_type`；信任要在 CLI 的 `/hooks` 里逐条确认（桌面应用的设置界面没有在源码里核对），按内容和位置记录，内容或位置变了就要重新确认，没确认的 hook 不运行。
  - 更正了原先的说法：只有 `SessionEnd` 被强制同步运行，`Interrupt` 照样在后台运行；`SessionStart` 和 `SessionEnd` 不带 `turn_id`（`SessionEnd` 也不带 `model`）；子代理的 hook 带的是根会话的 `session_id`，不是派出它的父会话的。
  - 还要用真实运行确认：某台 Windows 机器上 hook 实际由哪个 shell 执行（PowerShell 还是退回的 cmd；不带引号的写法两者都能运行，`& "…"` 的写法只能在 PowerShell 下运行）；Codex 内部的非子代理线程（例如审批复核）会不会把工具 hook 发到根会话上；`tool_use_id` 是否和会话文件里调用的 id 一致（`exec` 里跑的命令尤其不确定）；已经在运行的会话会不会接上新装的 hooks。
  - 所以第一版的 hooks 不建节点（hook 报的工具名和 id 可能和会话文件里的调用对不上）；用真实运行核对后再考虑让 hooks 提前显示工具节点。
- 权限确认之后到工具结束之前没有 hook，所以批准后那个工具节点和会话会一直显示“等待权限确认”，直到该轮次的下一个 hook（例如工具结束的 `PostToolUse`）或会话文件里该轮次的调用都结束。权限请求不带工具调用的 id，显示等待的是该轮次里最新一个还在执行的工具节点，并行调用时可能不是真正在等的那个。
- 派发子代理的调用找不到对应的子代理线程时（例如派出失败），派发节点在派出它的轮次进行中显示执行中，轮次结束后显示失败；之后子代理线程出现，就改为跟着它走。
- 追加给子代理的任务（`followup_task`、`send_message`），在逐步视角的因果链上接在子代理上一个任务的回复之后，而不是接在发出追加任务的那次调用上。

## Cursor

- 服务启动时会自动只读地打开 Cursor 的本地状态数据库，并每 3 秒查一次哪些会话变了。数据库不存在时视为没装 Cursor，跳过，不报错。
  - 默认位置：Windows `%APPDATA%\Cursor\User\globalStorage\state.vscdb`；macOS `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`；Linux `~/.config/Cursor/User/globalStorage/state.vscdb`。
  - 用环境变量 `AGENT_CANVAS_CURSOR_DB` 指定别的位置；设为空字符串表示不读取 Cursor。
- 对 Cursor 没有影响：数据库以只读方式打开，只做按主键的短查询，不写入、不持有长事务；数据库被占用或出错时这一轮放弃，下一轮重试，错误显示在诊断页。
- 读到的记录会裁剪后存进 agent-canvas 自己的数据库（文本、工具参数、工具结果各截到 64 KB）。之后的重建只用这份记录，不需要再读 Cursor 的数据库；Cursor 归档或删掉会话后，已采集的内容仍可看。
- 导入范围：未归档、至少有一条消息的 Agent 会话。**不导入**：已归档会话、没发过消息的空会话、云端 / 后台 Agent、Tab 补全。会话在 Cursor 里被归档或删除后，这里显示为“源文件已删除”。
- 子代理：Cursor 的子代理是单独的会话，这里显示在派出它的那一步（`task_v2`）下面，展开后是它内部的步骤。从同一个会话分叉出来的两个会话各自显示它们共用的子代理。
- 项目归属：按会话的工作目录归到项目，和同目录的 Claude Code、Codex 会话在同一个项目下；取不到工作目录时归到“Cursor（未知目录）”。
- 会话标题取 Cursor 给会话起的名字，没有时取第一条提示。
- 每一步的状态：Cursor 记录的完成 → 成功；出错 → 失败；终端命令退出码不为 0 → 失败；被用户拒绝执行 → 已拒绝；已取消、所在轮次结束时仍未完成、会话被中止 → 失败（详情里注明原因）。
- 会话状态只有运行中和空闲；“已结束”只在装了 hooks 且 Cursor 发出会话结束事件时出现。超过 15 分钟没有活动的“运行中”显示为“长时间无活动”。
- 更新延迟：不装 hooks 时取决于轮询间隔和 Cursor 多久把内容写进数据库，通常几秒。

### Cursor hooks（可选）

不装也能用。装上后，“开始运行”和“一轮结束”在 1 秒内到达，并且每次事件会立即催一次读库。

```
node packages/server/dist/cli.js hooks install --cursor      # 写入 ~/.cursor/hooks.json（不存在时新建）
node packages/server/dist/cli.js hooks uninstall --cursor    # 只移除本安装、本端口的那几条
```

- 只装 5 个观察类事件：`sessionStart`、`beforeSubmitPrompt`、`stop`、`subagentStop`、`sessionEnd`。每条的形状是 `{ "command": "…", "timeout": 5 }`。
- **不装任何能拦住操作的 hook**。Cursor 的权限类 hook（`preToolUse`、`beforeShellExecution` 等）在转发程序输出异常时会阻止 Cursor 的动作，所以这里一个都不装。代价是 Cursor 会话没有“等待权限确认”状态，工具开始执行的时刻靠读库得到。
- 选项和另外两个工具的一样：`--port <n>`、`--yes`（非交互终端必须加）、`--settings <file>`；环境变量 `AGENT_CANVAS_CURSOR_HOOKS_FILE` 改默认路径。`~/.cursor` 目录不存在时视为没装 Cursor，不做任何改动。文件里已有 `version` 且不是 1 时拒绝写入。
- 命令用绝对路径指向当前的 `node` 和这份 `cli.js`。Windows 上 Cursor 用 PowerShell 执行，命令写成 `& "<node>" "<cli.js>" hook-forward --origin cursor --port <n>`；其他平台是普通命令行。
- Cursor 监视 `hooks.json`，保存后自动生效，不需要确认信任；没生效时重启 Cursor。
- **移动、升级或删除 agent-canvas 之前，先运行 `hooks uninstall --cursor`**。否则 hook 命令指向不存在的文件，每次触发都会报错；这种情况下 Cursor 是否照常继续，还没有用真实的 Cursor 验证过。换了 node 之后重新运行一次 `hooks install --cursor`，它会把过期的条目换成新的。
- 这些 hook 是同步的：每次触发 Cursor 会等转发命令结束（启动一次 node，约 0.25 秒，Windows 上再加 PowerShell 的启动时间；服务没响应时最多约 1.3 秒）。5 个事件每轮各触发至多一次。
- 转发命令永远以退出码 0 结束，不读写文件；只在 `beforeSubmitPrompt` 时向 Cursor 输出 `{"continue":true}`（明确放行），其他事件不输出。
- hooks 只给出会话状态，不建、不改节点；节点一律来自数据库。存下来的 hook 内容不含你的邮箱（载荷里的 `user_email` 会被去掉），但包含提示正文，和另外两个工具的 hook 一样。

## Gemini CLI、Grok、Copilot CLI

**这三个来源未经真实数据核对。** 开发时手边没有这三个工具产生的会话，读法完全依据它们的公开源码、文档和第三方读取器写成，测试用的也全是自造的样例。真实数据的样子可能不一样：某些步骤缺失、标题或项目不对、用量偏差都有可能。觉得哪里不对时，先打开诊断页（见下文“诊断页”）看两处：该来源一栏里的**未识别的记录**（读到了但不认识的记录类型和次数），和 Hooks 一栏里的**被丢弃的外来 hook 调用**。

### 从哪里读

服务启动时，下面的目录存在才读取该来源，并持续监视；不存在时跳过，不报错、不创建任何东西。**该工具的会话目录（`~/.gemini/tmp`、`~/.grok/sessions`、`~/.copilot/session-state`）在服务启动之后才出现的，要重启服务后才会读取**——这个目录通常是工具第一次使用时才建的，所以“服务启动前就装好了工具、启动后才第一次用”也属于这种情况。诊断页会显示“存在，但服务启动时还没有这个目录，尚未读取”。对这三个工具的目录只读，从不写入。

| 来源 | 默认读取的目录 | 改位置 |
| --- | --- | --- |
| Gemini CLI（Google） | `~/.gemini/tmp/<项目目录名>/chats/` 下的 `session-*.jsonl`（旧版的 `session-*.json` 也读），子代理在 `chats/<会话 id>/` 下 | `AGENT_CANVAS_GEMINI_DIR`（指向 `.gemini` 这一层）；没设时用 Gemini 自己的 `GEMINI_CLI_HOME` 下的 `.gemini` |

| GitHub Copilot CLI | `~/.copilot/session-state/<会话 id>/events.jsonl` 和同目录的 `workspace.yaml`（1.0 以前的 `session-state/<会话 id>.jsonl` 也读） | `AGENT_CANVAS_COPILOT_DIR`（指向 `.copilot` 这一层）；没设时用 Copilot 自己的 `COPILOT_HOME` |

### 显示什么

- 和另外三种来源一样：用户输入、回复、思考、工具调用及结果、子代理、标题、模型、工作目录、token 用量（该工具有记录的部分）。会话按工作目录归到项目，和同目录的 Claude Code、Codex、Cursor 会话在同一个项目下；首页、检索、统计、文件页、异常页的来源筛选里各有一项。
- 来源标记是本项目自己画的字母（G、K、C），不是这些产品的标志。
- 检索、统计、按文件看、异常、导出与遮蔽照常工作，例外见下。
- Gemini CLI：标题取 Gemini 给会话写的摘要，没有时取第一条提示。工作目录取 `<项目目录名>/.project_root`，没有时查 `~/.gemini/projects.json`；这两个文件过大（超过 4 KB / 1 MB）或内容不是一个绝对路径时当作没有，项目显示为 `gemini:<项目目录名>`。在 Gemini 里回退（rewind）或删掉的消息，这里也随之消失；被回退掉的派发下面的子代理线程保留，改挂在会话下。只有元数据、还没有任何消息的会话文件不产生会话。
- Grok：标题取 `summary.json` 里 Grok 生成的标题，没有时取它的摘要，再没有时取第一条提示。子代理是单独的会话，这里显示为父会话的子代理线程（父会话还没读到时先等着，读到后再挂上；子代理的子代理也挂在最上层的会话里）。在 Grok 里回退的轮次会被移除。
- Copilot CLI：标题取 `workspace.yaml` 的 `name`，没有时取 `summary`，再没有时取第一条提示。工作目录取会话开始时的目录，之后切换目录不改变会话所属的项目。会话正常退出后显示“已结束”。

### 限制

- **没有 hooks**：不为这三个工具安装任何 hook，也就没有“等待权限确认”“等待输入”这类实时状态，“等待确认”类通知不会出现。会话状态只靠会话文件推断，延迟几秒：Gemini CLI 为运行中或空闲；Copilot CLI 为运行中，正常退出后为已结束；Grok 的文件里没有一轮结束的记号，会话一直是运行中。超过 15 分钟没有活动的“运行中”显示为“长时间无活动”。各种通知在这三个来源上能不能用，见“通知”一节末尾的表。
- **Gemini CLI**：Gemini 默认把 30 天以前的会话文件自动删掉，被删的会话在这里显示为“源文件已删除”，已采集的内容仍可看。旧版的整份 `.json` 会话照样读取（超过 64 MB 的不读，记在诊断页的“导入失败”里）；同一会话同时有新旧两种文件时只读新的。一个 Gemini 会话在活跃期间（最近有新内容、正在被读）在内存里约占会话文件大小的两倍，移出内存后释放；几百 MB 的会话文件会相应占用内存。统计里 `cached` 记为缓存读取，思考用的 token（`thoughts`）计入输出。
- **Grok**：一段很长的回复（或思考）显示为几个连续的节点，每满约 4,000 个字符接着一个新节点，内容不缺。token 用量来自每轮结束的记录（新输入 = `inputTokens + cacheCreationTokens`，缓存读取 = `cachedReadTokens`，输出 = `outputTokens + reasoningTokens`，对应关系是推测的），记在该轮最后一个回复节点上；一条用量记录都没有的 Grok 会话不参与“消耗异常高”的判断。
- **Copilot CLI**：只有整个会话的总用量，记在会话结束（`session.shutdown`）那一步上，不能按轮看 token。统计里这份总量算在会话退出的那一刻（按日统计时算在退出那一天），退出这一步不算任何轮次的一部分：一轮只算到它最后一个步骤，不会因为 CLI 开着几个小时才退出而被拉长。恢复会话（`session.resume`）之后没有新提示就继续做的事，算作单独的一轮。Copilot 会话不参与“消耗异常高”的判断（另外三类异常照常）。一个会话退出多次时，后一次只计比前一次多出来的部分，宁可少算也不多算。几个子代理同时运行时，分不清哪个线程属于哪次派发的，那几个线程挂在会话下，不连到派发的那一步。Copilot 自己修复会话文件时删掉的记录，这里已经显示过的步骤仍然保留。
- **会话目录在服务启动之后才出现**：要重启服务才会读取（见上）。
- 工具名和参数名按公开资料对照（哪些是读、写、改、执行、搜索、子代理），对照表之外的工具归为“其他”，仍显示名字、输入和输出。

### 钩子串扰

按公开资料，Grok 和 Copilot CLI 会读取 Claude Code（和 Cursor）的 hook 配置，因此可能调用我们为 Claude Code / Cursor 安装的 hook，但发来的内容是它们自己的格式。**它们实际会不会调用、发来什么，没有核对过。** 服务认出这种调用后直接丢弃（不存、不建会话），并在诊断页的 Hooks 一栏计数“被丢弃的外来 hook 调用”。这个数从服务启动时算起，重启后归零；不为 0 说明这次运行期间发生过这种情况，不影响数据，也不需要处理。

### 显示什么

- 和其他来源一样显示为会话：提问、回复、工具调用及结果、子代理线程、标题，以及该工具记下的思考、模型、工作目录和 token 用量（豆包没有后四样，见下）。检索、统计、按文件看、异常、导出与遮蔽照常工作；首页、检索、统计、文件页、异常页的来源筛选里各有一项（名称：DeepSeek、WorkBuddy、CodeBuddy、豆包），有会话才出现。

- **DeepSeek**：
  - 只有用户自己输入的消息算提问；工具注入的上下文不显示。一条消息里的几段文字之间换行。
  - 回复、思考、工具调用分别显示；工具结果按调用配对，出错的标为失败。
  - 上下文压缩显示为一个系统节点，压缩前的内容继续显示。一轮以出错结束时显示“Turn failed”，被中止时显示“Interrupted”，这一轮还在运行的调用标为失败。
  - 标题取 dsh 写下的最后一个标题，没有时取第一条提问。
  - 会话在中途切换工作目录时，显示的工作目录随之更新；所属的项目仍按会话开始时的目录。
  - 子代理是单独的会话文件，这里显示为根会话里的线程（多级子代理都挂在根会话下），并连到派出它的那次调用上；对不上时线程挂在会话下，不连线。子代理文件先于父会话被读到时先等着，读到父会话后再挂上。派给外部后端（例如 Codex）的子代理没有本地文件，只显示那次调用。

  - 只有人输入的文字算提问：客户端包在外面的提示、只含提醒或本地命令的段，以及引擎标为非人输入的消息都不显示。
  - 回复、思考、工具调用及结果分别显示；结果状态不是“完成”的标为失败。
  - 标题依次取：用户自己起的标题、自动生成的标题、话题，各取最后一条；都没有时取第一条提问。
  - 模型取每次回复记下的模型；记的是 `auto` 而会话里出现过具体模型时，显示具体的那个。

  - 第一条需求在 `trajectory.jsonl` 里没有对应的用户行时，用 `assignment.md` 里第一条需求的文字补一个提问节点。

### 限制

- **未经真实数据核对**（见本节开头；DeepSeek Harness 只核对过一个会话）。另外，[规格](./superpowers/specs/2026-11-17-more-sources-cn-design.md)第 9 节和三份格式说明的末尾列出了只有真实数据才能确定的问题，例如 DeepSeek 界面上的删除、编辑、回退在磁盘上做了什么、WorkBuddy 的用量在磁盘上的实际形状、豆包 `assignment.md` 的时间格式。
- **没有 hooks**：不为这四个工具安装任何 hook，也就没有“等待权限确认”“等待输入”这类实时状态，“等你确认权限”的通知不会出现。会话状态只靠会话文件推断，延迟几秒，只看主线（子代理线程不影响）；超过 15 分钟没有新内容的“运行中”显示为“长时间无活动”。各来源的差别：
  - **DeepSeek**：文件里每一轮都有开始和结束的记录。一轮进行中为运行中，结束后为空闲。因此“跑完了”照常；一轮以出错、被中止或中断结束时发“出错中断”；“卡住了”只在一轮进行中长时间没有动静时提醒。分叉出来的会话里复制过来的历史不算（读到分叉点之前一直是空闲），回放它不会发通知。
  - **WorkBuddy、CodeBuddy**：按资料，工具在一轮结束时可能写一条结束记录（`turn-metrics` 或 `acp-terminal-state`），但两者都是可选的、取决于运行它的宿主。**写了的**：读到它变为空闲，下一条提问又变为运行中，“跑完了”照常；`acp-terminal-state` 带错误时这一轮显示“Turn failed”并发“出错中断”（只带停止原因、不带错误的，只当正常结束）。只认当前分支上的结束记录，被回退掉的分支上的不算。后台任务的 `turn-metrics` 不算一轮结束。**从没写过的**：和 Grok 一样，会话一直是运行中，没有“跑完了”“出错中断”；“卡住了”打开时，会话停下后超过阈值会提醒一次，分不清是做完了还是卡住了。
  - **豆包**：文件里没有一轮结束的记号，和 Grok 一样一直是运行中，通知的情况也一样。行本身不带时间，会话的“最近活动”取每次读到新行时 `trajectory.jsonl` 的修改时间（节点的时间仍是需求的时间，见下）：一轮做得再久，只要还在写新行，就不算“长时间无活动”，也不会发“卡住了”；不再写新行超过阈值后才提醒。
  - “原地打转”“失败扎堆”在四个来源上都照常。
- **文件被重写**（四个来源都是）：
  - 只有文件变短、或已读部分开头或结尾的字节变了（DeepSeek 另加续读的位置上不是一个帧的开头）才认作重写；文件中间改了而两头没变，发现不了。
  - 认作重写后整个文件重新存一遍、会话重新推导。旧的那份留在数据库里，不删除，`agent-canvas compact` 也不回收（Grok 的重写也是这样）；豆包的 `assignment.md` 每变一次也整份存一次。所以数据库会随文件被重写的次数和豆包的轮数增长。
  - 一次回退或重写去掉几万个节点时（例如把一个 6 万行的 CodeBuddy 会话回退到很早的一条提问），服务会有一两秒不响应（一次测量约 1.7 秒）。只在那一次，数据不受影响。
- 文件一时打不开或读不了（Windows 上工具正在写、杀毒或备份软件占着）不算重写：这次什么也不读，诊断页“导入失败”里短暂出现一条，下次扫描（约 3 秒后）再读，读到后这一条自动消失。
- **项目与目录的大小写**：DeepSeek、WorkBuddy、CodeBuddy 三者之间，同一个目录只差大小写的写法归同一个项目（数据库里已有的项目和 Claude Code 的项目优先，否则以先遇到的写法为准）。但这三个来源与 Codex、Gemini CLI、Grok、Copilot CLI 第一次一起导入、又没有对应的 Claude Code 项目时，仍可能分成只差大小写的两个项目（以前的来源之间本来就是这样）。分开后不会自动合并。
- **从 0.2.0 退回 0.1.1**：存过这四个来源的会话之后，再用 0.1.1 打开同一个数据库，没有测试过。
- **DeepSeek Harness**：
  - **只读第 4 版的会话文件**（`session.v4.jsonl.zstd`）。只有更早版本文件的会话目录不读；旁边出现比 4 更高版本的文件时，只跳过那个文件，第 4 版照常读。这两种目录都计入诊断页的“有其他格式版本文件（不读）的会话目录”。
  - **需要 Node 22.15 或更高**：解压用的是 Node 自带的 zstd（22.15 起才有，标为实验性）。更早的 Node 上这个来源不启动，诊断页写明“需要 Node 22.15 或更高”。本项目声明的最低版本仍是 Node 22。
  - 文件中间有损坏时，读到损坏处为止，后面的内容不显示；损坏处之后变成可读的内容（例如工具修复了文件）会接着读。一帧解压后超过 64 MiB 的也当作损坏处理（dsh 写的一帧是一批追加的行，远小于这个数）。
  - 以分叉方式启动的会话和子代理，开头显示复制过来的历史（见上）。从分叉出来的会话再分叉出来的会话，在文件还在读的过程中可能短暂把复制来的轮次当成自己的，读完后正确。
  - “需要 Node 22.15 或更高”只在诊断页显示，启动时控制台不提示。
  - 用量里的输出是否对所有模型都已含思考，按资料推断，未核对。
- **WorkBuddy、CodeBuddy Code**：
  - **回退或“改写后重发”之后只显示当前分支**，被放弃的分支上的节点移除。**被放弃的分支上的用量不再计入统计**，虽然那些调用实际发生过。
  - 用量的换算**未经真实数据核对**：同一次回复的用量在文件里会出现在好几行上，按回复 id 只算一份（取最大的那份）；提示词数里已经含缓存时（OpenAI 式的字段），新输入 = 提示词数 − 缓存读取；否则（输入不含缓存，Anthropic 式），新输入 = 输入 + 缓存写入；输出含思考。认哪些字段名、哪种形状对应哪种上游，按引擎的类型定义推断，几个第三方工具在这一点上互相矛盾。
  - 一个节点被放弃之后，线程里又出现了很多后来的内容（超过约 26 万个字符的详情），它才回到当前分支时，节点照常显示，但内容可能标为读不出（服务只在内存里留着最近这么多的详情）。
  - 文件里没有任何一行带父节点 id 时，即使有回退标记也全部显示；找当前分支时遇到文件里没有的父节点，放弃挑选、全部显示，并在诊断页的未识别记录里计为 `workbuddy:dangling-parent` / `codebuddy:dangling-parent`。这两条是本项目的读法，不是对产品的描述（见格式说明第 7 节）。
  - 被截断或中止的工具调用（草稿）显示为失败。标题不随分支变化。派发子代理的工具按名字 `Task`、`Agent` 认，名字是推测的。
  - **工作目录必须出现在会话文件的前 16 MiB 里**，否则这个会话不读（子代理文件等它的主文件）。
  - 文件名不是 UUID 的主会话文件、文件名不以 `agent-` 开头的子代理文件不读，也不在任何地方计数。
  - 一轮不是由显示出来的提问开始时（引擎标为非人输入的消息、只有图片的提问等），这一轮进行中会话显示为空闲，结束时也没有“跑完了”。一条带错误的结束记录，到达时就在被放弃的分支上的，不显示“Turn failed”，那条分支后来回到当前分支也一样。
  - 会话目录在服务运行期间才出现的根（例如 WorkBuddy 的第二个根），重启后才读取。
- **豆包工作**：
  - **没有思考、模型、token 用量和工作目录**，这些地方留空；统计里豆包没有 token，不参与“消耗异常高”的判断（另外三类异常照常）。
  - 标题取第一条提问；所有会话在一个固定的项目“豆包工作”下。
  - 时间按需求逐轮取自 `assignment.md`，一轮里的节点时间相同，所以看不出一轮里每一步的耗时；工具调用没有耗时。只能用文件修改时间的线程在诊断页计数；这种线程的节点时间是第一次读到文件开头时的修改时间，以后不变。会话的“最近活动”另取每次读到新行时文件的修改时间（见上文“没有 hooks”）。
  - 一条需求超过 64 KiB 时，保留它的位置和时间（后面各轮的时间不受影响），文字只留前 64 KiB，末尾加“…”；它要补作第一条提问时，用的就是截短的文字。
  - 文件里没有一轮结束的信号：没有结果的工具调用一直显示为执行中。
  - **普通聊天和在云电脑上执行的任务在本机不留记录，读不到。**
  - 一个对话目录里没有或有多个 `m_` 开头的主代理目录时，这个对话不读，在诊断页计数。
  - 代理之间互发的消息没有资料，不处理。
- **按文件看**：四个来源的工具名和参数名对照表都**未经核对**（三份格式说明都没有给出参数名的可靠证据），按常见写法保守地认：
  - DeepSeek：读 `read`、`read_file`、`view`；写 `write`、`write_file`、`create`、`create_file`；改 `edit`、`edit_file`、`multi_edit`、`str_replace`、`replace`、`search_replace`、`apply_patch`；删 `delete`、`delete_file`、`remove_file`。路径参数依次试 `path`、`file_path`、`filePath`、`file`、`target_file`、`filename`；`apply_patch` 没有路径参数时取补丁文本里的文件。格式说明只证实了 `bash` 和 `subagent` 两个工具名。
  - WorkBuddy、CodeBuddy：读 `Read`、`read_file`；写 `Write`、`write_file`、`write_to_file`、`create_file`；改 `Edit`、`MultiEdit`、`NotebookEdit`、`edit_file`、`replace_in_file`、`search_replace`、`str_replace`；删 `Delete`、`delete_file`。路径参数依次试 `file_path`、`filePath`、`path`、`notebook_path`、`target_file`、`file`、`filename`。
  - 豆包：`Read`、`Write`、`Edit` 这三个工具名出自格式说明，参数名是猜的（依次试 `file_path`、`filePath`、`path`、`file`、`target_file`、`filename`）。没有工作目录，相对路径按原样显示。
  - 对照表之外的工具（命令行、搜索、子代理等）不算文件操作，仍显示名字、输入和输出。

### 不支持的

- **千问办公**：2026 年 11 月起改存数据库，新格式没有公开资料，等真实数据。
- **TRAE CLI**：记录的写法随版本变化，只有一个第三方工具作依据，等真实数据。
- **CodeBuddy 的 IDE 插件**：是另一种格式，不读。
- 上面四个工具的 hooks；DeepSeek Harness 第 4 版以前的会话文件；豆包的普通聊天和云电脑上的任务（见“限制”）。

## Qwen Code

**这个来源未经真实数据核对。** 开发机上没有 Qwen Code（阿里的命令行编码代理），读法完全依据它的开源代码（`QwenLM/qwen-code` 标签 `v0.27.4`）。依据和每条结论的出处写在格式说明 [`docs/formats/qwen-code.md`](./formats/qwen-code.md) 里，末尾列出了只有真实数据才能确定的问题。测试用的全是按这份说明自造的样例，测试通过只说明实现与对源码的理解一致，不说明与真实文件一致。觉得哪里不对时，先打开诊断页看 Qwen Code 一栏（见下文“诊断页”）。

### 从哪里读

读 Qwen Code“运行时目录”下的 `projects`，默认是 `~/.qwen/projects`：

| 文件 | 是什么 |
| --- | --- |
| `projects/<项目名>/chats/<会话 id>.jsonl` | 会话的主线 |
| `projects/<项目名>/chats/<会话 id>.title.json` | 会话的标题 |
| `projects/<项目名>/chats/archive/` 下的同名文件 | 归档的会话 |
| `projects/<项目名>/subagents/<会话 id>/agent-*.jsonl` 和同名的 `.meta.json` | 子代理的线程和它的说明 |

- 运行时目录取第一个有的：本程序的 `AGENT_CANVAS_QWEN_DIR`、Qwen Code 自己的 `QWEN_RUNTIME_DIR`、`QWEN_HOME`、默认的 `~/.qwen`。三个变量都指向 `projects` 的上一层；开头的 `~` 是主目录，相对路径按启动本服务时的工作目录解析。`AGENT_CANVAS_QWEN_DIR` 设为空字符串表示不读取 Qwen Code。
- **在 Qwen Code 的设置里改过输出目录的**（`advanced.runtimeOutputDir`）：本服务不读 Qwen Code 的设置，需要自己用 `AGENT_CANVAS_QWEN_DIR` 指过去。设的是绝对路径时就指向它；设的是相对路径（例如 `.qwen`）时，Qwen Code 在每个仓库里各放一份，本服务只能读其中一个，把 `AGENT_CANVAS_QWEN_DIR` 设成那个仓库下的这个目录（例如 `D:\work\app\.qwen`），其他仓库的不会自动找。
- 和其他只读会话文件的来源一样：服务启动时 `projects` 目录存在才读取并持续监视；不存在时跳过，不报错、不创建任何东西；**服务运行期间才出现的，重启服务后才读取**。对这个目录只读，从不写入。
- 只读上表里的文件。主线文件名必须是 32 到 36 个十六进制字符或连字符（Qwen Code 自己的规则），别的名字不读。`workflows/`、`tmp/` 下的文件，`.runtime.json`、`.worktree.json`、`.pr.json`、`.jsonl.stream` 都不读。
- 会话被归档（移到 `chats/archive/`）或取消归档时，这里看到的还是同一个会话，不重读、不重复，也不会显示为“源文件已删除”。两处同时有同一个会话时读 `chats/` 下的。

### 显示什么

- 和其他来源一样显示为会话：提问、回复、思考、工具调用及结果、子代理线程、标题、模型、工作目录、token 用量，以及上下文压缩的位置。检索、统计、按文件看、异常（包括“消耗异常高”）、导出与遮蔽照常工作；首页、检索、统计、文件页、异常页的来源筛选里有一项“Qwen Code”，有会话才出现。
- 来源标记是本项目自己画的字母 Q，不是 Qwen Code 的标志。
- 会话 id 就是 Qwen Code 自己的会话 id。
- **项目**：按记录里的工作目录归，和同一目录下的 Claude Code、Codex、DeepSeek 等会话在同一个项目里。Qwen Code 给目录起的名字（有损的编码）不用。工作目录在 `<仓库>/.qwen/worktrees/` 下时（Qwen Code 的工作树），项目取那个仓库，会话的工作目录本身照原样显示。同一个目录只差大小写的写法，和 DeepSeek、WorkBuddy、CodeBuddy 一起按上一节“项目与目录的大小写”处理。
- **提问**：按 Qwen Code 自己显示的文字（它在发给模型的文字后面加的钩子上下文、引用文件的内容不显示）；显示出来的文字为空的提问仍是一条提问。后台任务完成、定时任务这类系统发来的消息显示为系统节点。斜杠命令（不隐藏的）显示为一个系统节点，内容是命令本身。
- **回复**：思考、文字、工具调用按顺序分别显示；图片显示为 `[image]`。模型取每次回复记下的模型。
- **工具调用**：结果按调用 id 配对（没有 id 时按工具名配同一条回复里的调用）；出错的标为失败，被取消的也标为失败（节点详情的“原始记录”里有 `cancelled: true`）；没有结果的调用显示为执行中。
- **上下文压缩**显示为一个系统节点 `Compact`，文字是 `Context compressed: A → B tokens`（A、B 是压缩前后的 token 数），压缩前的内容继续显示。
- **标题**依次取：文件里最后一条改标题的记录（不管它在不在当前分支上）；标题文件，仅当它是手动或自动起的；第一条提问。标题文件被删掉后，已经读到的标题照旧显示；标题文件被改成同样大小的另一个标题时，只有服务运行中当场看到这次修改才更新（定期的全量扫描按大小判断，看不出）。
- **子代理**：`subagents/<会话 id>/` 下的线程归到这个会话，按说明文件连到派出它的那次 `agent` 调用（嵌套的子代理连到它的父代理线程里的调用）；没有说明文件时按线程 id 末尾的调用 id 连；对不上时线程挂在会话下，不连线。说明文件、线程、主线谁先被读到，结果都一样（子代理文件比主线文件先出现时，要等下一次全量扫描才读到，最多一分钟左右）。分叉式子代理继承来的整段上下文不显示。
- **用量**：缓存读取 = `cachedContentTokenCount`；新输入 = `promptTokenCount − cachedContentTokenCount`（缓存写入没有存下来，分不出来）；输出照 Qwen Code 自己的算法，在“总数 − 提示”和“候选”“候选 + 思考”之间取，取法和这次会话用的认证方式有关。
- **会话状态**：只看主线的当前分支。最后是一条提问时为运行中；最后是一轮的结果记录（`turn_result`）时为空闲；这一轮出错时加一个“Turn failed”系统节点，被取消时加“Interrupted”，两种都发“出错中断”。“跑完了”照常。
- 用 `/branch` 复制出来的会话、另开的子会话，都显示为独立的会话。

### 限制

- **未经真实数据核对**（见本节开头）。依据是 `v0.27.4` 的源码，见 [`docs/formats/qwen-code.md`](./formats/qwen-code.md)。
- **没有 hooks**：不为 Qwen Code 安装任何 hook，没有“等待权限确认”“等待输入”这类实时状态。会话状态只靠会话文件推断，延迟几秒；超过 15 分钟没有新内容的“运行中”显示为“长时间无活动”。
- **不写一轮结果记录的版本**：较早的 Qwen Code 不写 `turn_result`。这样的会话有提问就一直是运行中（和 WorkBuddy、CodeBuddy 没写结束记录时一样），“跑完了”“出错中断”都不会发；“卡住了”打开时，会话停下后超过阈值会提醒一次。
- **托管会话不读**：文件开头是托管会话记录的，不显示，在诊断页计数“托管会话（格式不支持，没有读取）”；它的子代理文件也不读。
- **0.4.0 以前的旧文件不读**（`tmp/<哈希>/chats/session-*.json`），也不计数。
- **回退之后只显示当前分支**：Qwen Code 回退（`/rewind`）、改写后重发、删除消息组之后，被放弃的分支上的节点移除。**被放弃的分支上的用量不再计入统计**，虽然那些调用实际发生过。当前分支按 Qwen Code 自己的规则求：从文件里最后一条对话记录往回走；走到文件里没有的父记录时停下，更早的记录不显示（诊断页的未识别记录里计为 `qwen:history-gap`）。
- **`/branch` 复制出来的会话带着原会话的内容和用量**：跨会话相加（统计页的总量、按项目、按来源）时，复制过来的那部分会重复计算。
- 一个节点被放弃之后，线程里又出现了很多后来的内容（超过约 26 万个字符的详情），它才回到当前分支时，节点照常显示，但内容可能标为读不出（和 WorkBuddy、CodeBuddy 相同）。被放弃的分支回到当前分支时（Qwen Code 的操作不会这样做），它的结果可能再通知一次。
- **同一个 id 的多行**（Qwen Code 当前版本不写，较早或其他写入者可能写）：只有回复会合并成一条；其他记录的这种后续行忽略，在诊断页的未识别记录里计为 `qwen:fragment-ignored`。
- **子代理的用量**：子代理线程只用它自己记录里的认证方式，不借用主线的；按 Qwen Code 的格式，子代理的记录上没有认证方式，所以实际上按“认证方式未知”的那一种算法换算，可能和 Qwen Code 自己算的不同。子代理的说明文件写着一个对不上任何调用的派发 id 时，这个线程挂在会话下，不连线（不再按线程 id 末尾去猜）。
- **按文件看**：没有逐个核对 Qwen Code 各工具的参数名。按保守的对照表认：工具名里有 `write` 的算写，有 `edit` 或 `replace` 的算改，有 `read` 的算读（例如 `read_file`、`write_file`、`replace`、`edit`，名字未经核对）；路径参数依次试 `file_path`、`absolute_path`、`path`。其他工具（命令行、搜索、子代理等）不算文件操作。
- **找会话的工作目录时，超过 64 KiB 的行跳过**（例如带着引用文件内容的第一条提问）：这时项目取自后面的记录。文件里还没有一条不超过 64 KiB 的记录时，这个会话完全不显示，诊断页也没有提示；有了这样一条记录才出现。
- **删除消息组删掉了派出子代理的那次调用**：子代理的文件还在，它的线程留在会话里、不连线，它的用量仍然计入统计。
- **同一个会话 id 出现在两个项目目录下**（Qwen Code 自己不会这样写，复制了 `projects/` 下的一个项目目录时会这样）：只读一份。已经读过、存进数据库的那一份优先；都没读过时，读目录名按字符编码排在最前的那一份。另一份（连同它的标题文件和子代理文件）不读，在诊断页计入“在另一个目录或配置里重复出现、只读了一份的会话”。读的那一份被删掉后，下次扫描改读另一份，会话不显示为“源文件已删除”。选哪一份只看是否读过和目录名，不看哪一份更新，所以都没读过时可能读到旧的那份。被删的那一份后来又放回原处的话，两份都已读过，重启后可能换读另一份，之后追加的内容可能接不上已有的内容而单独显示；这时删掉多余的那个目录再重建即可。
- **诊断页里 `qwen:` 开头的未识别记录**：`qwen:history-gap`（往回走时缺父记录）、`qwen:history-cycle`（父记录绕成环）、`qwen:fragment-ignored`（同一个 id 的后续行被忽略）、`qwen:orphan-result`（找不到对应调用的工具结果）、`qwen:session-mismatch`（主线文件里会话 id 不符的行）、`qwen:invalid-json`（不是 JSON 的行）、`qwen:invalid-record`（缺必需字段的记录）、`qwen:normalizer-error`（处理时出错）。
- 文件被重写（例如删除消息组）后整个重新存一遍、会话重新推导；旧的那份不回收；一次去掉很多节点时服务会短暂不响应。这几条和上一节一样，见“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”一节“限制”里的“文件被重写”。文件一时打不开不算重写，下次扫描再读。
- Qwen Code 的钩子、`workflows/`、`tmp/`、按项目各放一份的输出目录（见上）都不读。
- **从 0.3.0 退回 0.2.0**：存过 Qwen Code 的会话之后，再用 0.2.0 打开同一个数据库，没有测试过。

## 按文件看

除了按时间看一个会话，还可以按文件看。

**会话里的文件面板**：会话页顶栏的“文件”按钮，打开右侧的文件面板。

- 列出这个会话读过、改过的文件（含子代理内部动的），显示相对于会话工作目录的路径、读了几次、改了几次、最近一次的时间。
- “只看改过的”默认打开（读过但没改的通常很多）；可以按路径过滤，按改动最多、最近、路径排序。
- 点一个文件展开它涉及的每一步；点某一步，在画布上选中并定位到它（概览视角下定位到它所在的轮次，并在下方的瀑布图里选中这一步）。
- 文件面板和节点详情的抽屉共用右侧的位置，同时只显示一个。
- 地址 `#/s/<会话 id>/f/<路径>` 直接打开某个会话里的某个文件。

**文件页**：顶栏的“文件”，按项目看哪些文件被动过。

- 筛选：项目、来源、时间范围、“只看改过的”、路径过滤、排序。一次最多显示 200 个文件，多出来时用过滤框缩小范围。
- 点一个文件，列出动过它的会话（来源、标题、次数、最近时间），点击跳到那个会话里的这个文件。
- 一个文件属于哪个项目，按动它的会话所在的项目算。

**算什么、不算什么**：

- 只统计读写文件的专用工具，路径来自工具参数里的结构化字段。**命令行里的文件操作不算**（`cat`、`sed`、重定向等写法太多，猜错比不显示更糟），所以用命令行改的文件在这里看不到。搜索和列目录也不算。
- **失败或被拒绝的调用不计入次数**，也不会让文件显示为“改过”。它们仍然出现在文件的步骤列表里，标为失败；文件行上会有“失败 N”的标记。
- 同一个文件的不同写法（斜杠方向、盘符大小写、`.` 和 `..`、相对路径）会被认成同一个；Windows 上不分大小写。
- 只存路径和动作，不存文件内容。

各来源能看到什么：

| | Claude Code | Codex | Cursor |
| --- | --- | --- | --- |
| 读 | ✅ `Read` | ❌ Codex 用命令行读文件，没有结构化记录 | ✅ `read_file_v2` |
| 改 | ✅ `Edit`、`NotebookEdit` | ✅ 每次补丁后的文件改动记录 | ✅ `edit_file_v2` |
| 新建 | ⚠️ `Write` 分不清新建还是覆盖，统一显示为“写入” | ✅ | ⚠️ 分不清，算作“改” |
| 删除 | ❌ 没有专用工具 | ✅ | ✅ `delete_file` |

Gemini CLI（`read_file`、`write_file`、`replace` 等）、Grok（`read_file`、`write`、`search_replace`、`apply_patch` 等）、Copilot CLI（`view`、`create`、`edit`、`apply_patch`）的读、写、改工具同样计入；它们的工具名和参数名取自公开资料，未经真实数据核对。DeepSeek、WorkBuddy、CodeBuddy、豆包、Qwen Code 的对照表是按常见写法猜的，同样未经核对，具体认哪些名字见“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”和“Qwen Code”两节的“限制”。

## 统计

顶栏的“统计”打开统计页，汇总全部会话。顶部可以选时间范围（最近 7 天、最近 30 天、全部）、来源和项目，选择记在这个浏览器里。

页面内容：总量、按天（范围超过两个月时按周）的活跃时长、各来源的对比、时间花在哪类工具上、最慢的 10 次调用、最常失败的工具、按项目的汇总。

每个数字的口径：

| 指标 | 怎么算 |
| --- | --- |
| 会话 | 范围内有轮次开始的会话数 |
| 轮次 | 主线程上的轮次数，和会话页上的轮次卡片一一对应；子代理内部的不算。一轮属于它开始的那一天 |
| 活跃时长 | 各轮次的时长之和。一轮的时长 = 最后一个节点结束的时间 − 提示的时间；还在进行的轮次算到现在，但超过 15 分钟没有动静就不再增长。它不是你坐在电脑前的时间 |
| 工具调用 | 工具节点和子代理派发节点的数量，**含子代理内部的调用**（所以会比会话页轮次卡片上的数多） |
| 失败率 | 失败或被拒绝的调用 ÷ 已结束的调用；还在执行的不算 |
| 工具耗时 | 各次调用的耗时相加。并行的调用各算各的，所以合计可以比活跃时长还长 |
| token | 分三类，三种来源按同一口径归类，见下 |

token 的三类：

| 分类 | 含义 | Claude Code | Codex |
| --- | --- | --- | --- |
| 新输入 | 模型新处理的输入（不是从缓存读的） | `input_tokens + cache_creation_input_tokens` | `input_tokens − cached_input_tokens` |
| 缓存读取 | 从缓存里读的输入 | `cache_read_input_tokens` | `cached_input_tokens` |
| 输出 | 模型的输出（含推理） | `output_tokens` | `output_tokens` |

- 两家原始记录里的“输入”含义不同（Claude Code 的不含缓存读取，Codex 的包含），所以这里拆开再归类，否则两边的数字没法比。会话页和复盘视角里的 token 用的是同一套分类。
- Cursor 的数据库不记录每一步的 token（计数全为 0），所以 Cursor 的 token 显示为“—”。
- Gemini CLI、Grok、Copilot CLI 的归类方法和限制（Copilot CLI 只有会话总用量）见“Gemini CLI、Grok、Copilot CLI”一节；DeepSeek、WorkBuddy、CodeBuddy、豆包的见“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”一节，Qwen Code 的见“Qwen Code”一节（`/branch` 复制出来的会话跨会话相加时会重复计算）。
- 不换算成金额：各家的价格和套餐不同。
- 工具名按各来源自己的叫法显示，不跨来源合并（`Bash`、`exec`、`run_terminal_command_v2` 不是同一个东西）。各来源的对比用的是每轮中位时长、每轮平均调用数、失败率这类不依赖名字的指标。
- “最慢的 10 次调用”每一行可以点开那个会话（目前不会自动定位到那一步）。“最常失败的工具”里调用不足 5 次的不上榜。
- 统计只用已经推导好的节点，不含任何对话内容；接口 `GET /api/stats?range=7d|30d|all&origin=…&projectId=…` 返回的也只有计数、时长、名字和 id。
- 性能：每个会话的小结会缓存，只有变过的会话才重算；服务启动完成后会在后台预先算好，所以打开页面通常是即时的。启动导入或重建还在进行时，页面会提示数字仍在变化。

## 异常

统计页看的是总体，这里看的是**单个会话内部值得回头看一眼的模式**。四类，全部是固定规则，不用模型判断：

| 类型 | 判定 |
| --- | --- |
| 原地打转 | 一轮里，同一个调用失败了 3 次以上；或同一个调用连续执行了 5 次以上（中间没有别的工具调用） |
| 失败扎堆 | 一轮里连续 5 次以上工具调用失败（被你拒绝的不算失败，也不打断连续） |
| 反复改同一个文件 | 一轮里同一个文件被改了 15 次以上（失败的不算） |
| 消耗异常高 | 主线的一轮结束后，它的工作时间或 token 超过同项目、同来源历史 95 分位的 3 倍，并且超过 10 分钟 / 20 万 token |

- “同一个调用”指工具名相同、**完整输入**也相同（比较的是输入的哈希，不存内容）。Cursor 的编辑调用输入里只有文件路径，所以还要改前、改后的内容也相同才算同一个调用。
- “一轮”是从一条提示到下一条提示之前。子代理内部的步骤各自成轮，同样检测，异常记在它所属的会话上。
- “工作时间”是这一轮里工具、子代理、思考的耗时之和，不含等你回复的时间。历史不足 20 轮的项目不判“消耗异常高”；Cursor 没有 token 数据，只看时间；Copilot CLI 只有会话总用量，不判这一类；一条用量记录都没有的 Grok 会话也不判、不进基线。基线会随数据变化，所以这一类的旧结果可能略有变动。
- 这些是启发式规则，**会有误报和漏报**：故意反复跑同一个测试会被算作原地打转；用命令行改文件不计入“反复改同一个文件”。阈值是固定的，暂不能自定义。

在哪里看：

- 首页：有异常的会话卡片上有一个“!”标记和条数，悬停看各类各几条。
- 会话页：出异常的轮次卡片和子代理卡片上有标记；工具栏的“异常”按钮打开面板，列出每一条（类型、第几轮、依据和次数、时间，改文件的那类带路径），点一条定位到相关的那一步。回放时画布只标回放时间之前的异常。
- 顶栏的“异常”（`#/anomalies`）：跨会话的列表，可按时间范围、来源、项目、类型筛选，最多列最近 200 条。
- 通知：见下一节的“原地打转”和“失败扎堆”。另外两类是事后才能判断的，只在页面上标。

异常记录里只有类型、次数、时间、节点 id、工具名和文件路径，不含对话内容。

## 导出与分享

把一个会话导出成一个文件发给别人看。会话页工具栏的“导出”打开对话框：

- **格式**
  - **HTML**：一个双击就能在浏览器里打开的文件，里面是这个会话的只读画布（概览和其他视角、瀑布图、每一步的详情、回放）。对方不用装任何东西。文件完全自包含，**打开时不联网**，不请求任何外部资源；会话里的内容只当文字显示，不会被当成网页代码执行。导出文件里没有“文件”和“异常”面板。文件本身至少 2 MB（查看器），再加上会话的数据。
  - **Markdown**：按时间线性排列的文字记录——每轮的提示、回复、每一步的工具名、输入和输出。为了保证贴到任何地方都不会被渲染成标题、链接或网页代码，会话里的文字全部放在代码块里，读起来比较“硬”。
- **范围**：整个会话，或只导出当前选中的这一轮（连同这一轮派出的子代理）。
- **内容**：是否包含思考、是否包含子代理内部的步骤；工具输出保留每步前 8 KB（默认）、全部或不含。
- **遮蔽**：见下一节。对话框会先扫描一遍，列出找到了哪些类型、各几处（只有类型和数量，不显示内容）。
- **大小**：预计大小显示在对话框里；超过 50 MB 不能导出。很大的会话（几万步以上）整个导不出来，请只导出一轮，或者不含工具输出。

导出的文件里**不包含**：原始记录、hook 的载荷、其他会话的任何数据。会话 id 保留；工作目录、分支、项目 id 按遮蔽选项处理。

2026-11-13 在一份真实数据上测得（一次测量，不是保证）：一个 5,500 步的会话，Markdown 13 MB、约 2 秒，HTML 22 MB、约 3 秒；40 个会话里有 4 个因为太大不能整个导出。

导出接口只接受本页面发起的请求，其他网页（包括本机上别的端口的页面）不能触发导出。

## 遮蔽敏感信息

导出时把密钥之类的内容替换成占位符，例如 `‹已遮蔽·OpenAI key#1›`。同一个值在一次导出里编号相同，读的人能看出两处是同一个值，但看不到值本身。

**四个类别**，在导出对话框里各有开关：

| 类别 | 内容 | 默认 |
| --- | --- | --- |
| 固定格式的凭据 | 各家 API key（Anthropic、OpenAI、Google、Stripe、Hugging Face 等）、GitHub / GitLab / Slack / npm token、AWS key 和 secret、Google OAuth 令牌、JWT、`Authorization` 头（Bearer / Basic / Token）、Cookie 的值、私钥块、网址里的密码、命令行里的密码（`curl -u`、`mysql -p`、`docker login -p`、`sshpass -p`）、SQL 里的密码、`.netrc` 的密码、Azure 存储密钥 | 开 |
| 密钥/密码赋值 | 名字里带 password、secret、token、api key、access key、private key 等的变量或字段后面的值。值是占位符、变量引用、明显是代码（函数调用、类型名、日期）的不遮；`max_tokens`、`input_tokens` 这类 token 计数不算 | 开 |
| 个人信息 | 邮箱地址；主目录路径里的用户名（换成 `~`） | 关 |
| 自定义词 | 你自己列的词（公司名、内部域名、项目代号），原样匹配，不分大小写；每个至少 3 个字符，最多 100 个。在导出对话框里编辑，存在数据目录的 `export-settings.json` 里。这个文件损坏时，带自定义词的导出会被拒绝而不是照常导出，重新保存一次即可 | 有词就开 |

- 一处被认出的值，如果足够像密钥（够长、字符种类够多、不是路径或普通单词），这次导出里其他地方出现的同一个值也会被遮。
- 遮蔽出错时宁可多遮：那段文字整体换成 `‹已遮蔽·处理失败›`，不会输出原文。

**遮蔽是尽力而为，不保证遮全。分享前请自己再看一遍。** 已知会漏的情况：

- 不带引号、全是小写字母、不含数字的密码（`PASSWORD=correcthorse`），以及由几个普通单词组成的口令；
- 没有固定前缀、也不跟在密钥名后面的令牌（比如各种无前缀的随机串）——“看起来随机的长字符串”不会被当成密钥，因为哈希和 id 到处都是；
- 经过 base64、网址编码等编码之后的密钥；
- 图片、PDF 等二进制内容里的文字；
- 写在句子里的密码（“密码是 xxx”）；
- 纯文字里嵌在密钥名下面的 JSON 对象里的值（结构化的工具输入输出里会遮）；
- 被截断得只剩前几个字符的密钥。

反过来也会多遮：比如 i18n 文件里 `"login.password": "Password"` 的值会被遮掉。

### 页面上的遮蔽开关

顶栏的“遮蔽”开关（状态记在这个浏览器里，默认关），适合投屏、截图时打开。打开后，页面上来自会话的文字——卡片摘要、详情、原始记录、检索片段、文件路径、统计和异常页里的内容、浏览器标签页标题——都按“固定格式的凭据”“密钥/密码赋值”“自定义词”三类遮蔽后显示；个人信息不遮。

- 打开会话时，页面会先向服务请求“这个会话里认出的敏感值”，顶栏短暂显示“正在识别…”；很大的会话第一次要几秒。识别不全时顶栏有一个 ⚠ 提示。
- 检索仍按原文匹配；命中落在被遮蔽的内容里时，高亮显示在占位符上。
- 复制出来的也是遮蔽后的文字；开关打开时自定义词的编辑框会隐藏。
- **它防的是屏幕上被看到**，不是防本机上的其他程序：数据库里仍是原文，接口仍返回原文，浏览器的开发者工具里也能看到原文；开关打开之前就打开的地址栏内容不变；通知不受影响。

## 通知

会话需要你的时候，在桌面上弹一条系统通知。**默认关闭**，在页面顶栏的“通知”里打开；设置保存在本机，重启后还在。

六种提醒，各有开关：

| 种类 | 什么时候弹 |
| --- | --- |
| 原地打转 | 正在运行的会话里刚出现“原地打转”（判定见上一节“异常”）。同一轮只弹一次；多处同时出现时合成一条（“…，等 N 处”） |
| 失败扎堆 | 正在运行的会话里刚出现“失败扎堆”。规则同上 |
| 等你确认权限 | 会话进入“等待权限确认” |
| 跑完了 | 会话从运行中变成空闲，且这一轮至少跑了“最短时长”（默认 60 秒，填 0 表示每一轮都提醒）。为了分清是正常结束还是出错，会晚 3 秒发出 |
| 出错中断 | 一轮以错误或中断结束。这时不再另发“跑完了” |
| 卡住了 | 会话显示运行中，但超过“卡住阈值”（默认 15 分钟）没有任何动静。每次卡住只提醒一次 |

- 通知的标题是“种类 · 项目名”，正文是会话标题加一句补充（例如“用时 3 分 20 秒”）和来源。**不含**提示、工具参数、输出等对话内容，因为通知会显示在锁屏和通知中心里。
- 点击通知会在浏览器里打开那个会话（Windows）。macOS 的系统限制使这种通知不能带点击跳转，网址写在正文里；Linux 取决于桌面环境。
- 不会弹的情况：启动时导入历史、升级后的重建、读入很久以前的会话（只有两分钟内新发生的事才提醒）；同一件事只弹一次，同一个会话同一种提醒 30 秒内最多一条。
- “原地打转”和“失败扎堆”点击后会打开会话并定位到相关的那一步；打开开关之前已经存在的异常不补弹。
- 服务重启后不补发重启前的事。重启时正在运行的会话会被接着跟踪（只跟踪最近 24 小时内有过活动的）。
- Windows 上通知的横幅停留约 25 秒，之后收进通知中心（`Win + N` 打开）；开着“请勿打扰”时不弹横幅，直接进通知中心。
- “发一条测试通知”可以随时用，不受总开关影响。
- 发不出去时（系统不支持、被系统的通知设置或专注模式拦住等）服务照常工作；设置页和诊断页会显示投递状态和最近一次错误。注意：系统的通知设置把它静音时，这里仍可能显示“已发出”。
- 不引入额外的程序：Windows 用系统自带的 PowerShell 调通知接口，macOS 用 `osascript`，Linux 用 `notify-send`（没有这个命令时不可用）。通知只在本机弹出，不联网。

各来源的差别：

| | Claude Code | Codex | Cursor |
| --- | --- | --- | --- |
| 等你确认权限 | 需要装 hooks | 需要装 hooks 并确认信任 | 没有这个状态 |
| 跑完了 | ✅ | ✅ | ✅（不装 hooks 时晚几秒，用时可能略有出入） |
| 出错中断 | ✅ 用户中断；接口报错需要装 hooks 才看得出来 | ✅ | ⚠️ 只有中止时正好有工具在运行才看得出来，否则会被当成“跑完了” |
| 卡住了 | ✅ | ✅ | ✅ |

只读会话文件的八个来源没有 hooks，都没有“等你确认权限”；其余几种按会话文件判断，晚几秒，能不能用取决于文件里有没有一轮结束和出错的记号：

| | Gemini CLI | Grok | Copilot CLI | DeepSeek | WorkBuddy、CodeBuddy | 豆包 | Qwen Code |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 跑完了 | ✅ | ❌ 会话一直是运行中 | ❌ 会话只有运行中和已结束 | ✅ | ⚠️ 只在工具写了一轮结束的记录时 | ❌ 同 Grok | ⚠️ 只在 Qwen Code 写了一轮的结果记录时（较早的版本不写） |
| 出错中断 | ❌ 文件里没有出错的记号 | ❌ | ⚠️ 被中断的一轮，只在中断后两分钟内会话退出时 | ✅ 出错、被中止、中断 | ⚠️ 只在结束记录带错误时 | ❌ | ⚠️ 出错、被取消；同样只在写了结果记录时 |
| 卡住了 | ✅ | ⚠️ 会话停下后超过阈值都会提醒一次 | ⚠️ 同 Grok，直到会话退出 | ✅ | 写了结束记录时 ✅，否则同 Grok | ⚠️ 同 Grok（“停下”按文件不再出现新行算） | 写了结果记录时 ✅，否则同 Grok |

“原地打转”“失败扎堆”在这些来源上都照常。细节见“Gemini CLI、Grok、Copilot CLI”“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”“Qwen Code”三节的“限制”。

## 待处理

顶栏的“待处理”（`#/attention`）列出此刻需要你出手的会话：在等你批准、出错停了、卡住了、跑完一轮在等你说下一句。顺利运行的会话不在列表里。

- 顶栏“待处理”旁边的数字是列表里的条数，为 0 时不显示；在哪一页都随会话变化实时更新。首页的“N 个正在进行”也指向这一页。
- 列表实时更新，不用刷新。只由时间引起的变化（变成“卡住了”、超过时限被移出）在一分钟内出现。
- 这一页与通知的开关无关：通知关着时它照样工作。

四种，一个会话同一时刻最多一种，排在前面的优先；列表也按这个顺序排，同一种里新的在前：

| 种类 | 什么时候出现 | 时间从哪一步算起 |
| --- | --- | --- |
| 等你批准 | 会话在等待权限确认。子代理的批准请求也算，点进去定位到子代理里的那一步 | 进入等待的那一步 |
| 出错中断 | 会话已停下，最近一个提问之后的这一轮以出错或中断结束：出错的记号之后主线上没有别的步骤（Cursor 对话被中止时正在运行的调用除外：它后面的步骤是中止之前写下的）。怎样算出错与通知完全相同 | 出错的记号 |
| 卡住了 | 会话显示运行中，但超过“卡住阈值”没有任何动静（子代理还在动不算没有动静） | 主线最后一步 |
| 跑完了 | 会话已停下，且不是出错中断 | 主线最后一步 |

- “已停下”包括空闲和等待输入。装了 hooks 的 Claude Code 在一轮结束约一分钟后会变成“等待输入”，它与之前的“跑完了”（或“出错中断”）是同一条，不会因此重新出现。
- 卡住阈值就是通知设置里的“卡住阈值”（默认 15 分钟），通知关着时也用它。它与首页卡片上的“长时间无活动”（固定 15 分钟）可能不同。
- 不列出的：已结束的、源文件已删除的、正在运行且没有超过阈值的，以及主线上还没有任何提问的会话。
- 时间只按主线的步骤算。hooks、子代理、一轮结束后才写进文件的记录不会把一条往后推。
- “跑完了”没有最短时长：再短的一轮跑完了也是在等你。

每一行写着种类、来源、项目和多久之前，下面一行说明为什么（前面带“要执行：”“这一轮没有正常结束：”“最后一步：”“最后的回复：”）：

- 等你批准：那一步的工具名和它要做的事——命令或文件路径（从调用的参数里取；取不出来时是参数的开头）；
- 出错中断：出错那一步的标题或摘要，用户中断时也是这一句。只由 hooks 报告、没有对应步骤的出错，写 hooks 给出的原因：Claude Code 的 `StopFailure` 写“接口报错”（hooks 带了错误代码时加在括号里，如“接口报错（rate_limit）”），Codex 的 `Interrupt` 写“被中断”，Cursor 的 `stop` 写“出错”或“对话被中止”；点进去定位到主线的最后一步；
- 卡住了：最近一步的标题；
- 跑完了：最后一段回复的开头。

找不到这样一步时（例如等你批准但还没有对应的调用，或这一轮没有回复），这一行不显示。

说明最多 200 个字。它是对话内容，按顶栏的“遮蔽”开关遮蔽，与会话卡片、画布相同。点一行打开那个会话，并定位到相关的那一步；点“知道了”不会打开。

**知道了与自动移出**

- “知道了”把这一条移出列表。会话再次需要你时算新的一条，会重新出现。例如你回复之后它又跑完一轮；或者同一轮里迟到的出错记号把“跑完了”变成“出错中断”。
- 超过时限没处理的自动移出。时限默认 24 小时，在页面上改，可以是 1 到 720 之间的整数（小时），改了立即生效。
- “显示已移出的”列出两种被移出的，注明是“你点了知道了”还是“超过 N 小时没处理”，前者可以撤销。它只列 30 天内的，更早的不再显示，相应的“知道了”记录也会删掉。这个列表在打开时才向服务读取。
- 这些记在服务的数据库里：不同浏览器、多个窗口看到的相同，重启服务、重建数据库后不变。

各来源能出现哪几种（与“通知”一节的两张表对应，认不认得出取决于同样的记号）：

| | Claude Code | Codex | Cursor |
| --- | --- | --- | --- |
| 等你批准 | 需要装 hooks | 需要装 hooks 并确认信任 | 没有这个状态 |
| 跑完了 | ✅ | ✅ | ✅ |
| 出错中断 | ✅ 用户中断；接口报错需要装 hooks 才看得出来 | ✅ | ⚠️ 中止时正好有工具在运行，或装了 hooks 时 `stop` 报告出错或中止，才看得出来；否则显示为“跑完了” |
| 卡住了 | ✅ | ✅ | ✅ |

只读会话文件的八个来源都没有“等你批准”：

| | Gemini CLI | Grok | Copilot CLI | DeepSeek | WorkBuddy、CodeBuddy | 豆包 | Qwen Code |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 跑完了 | ✅ | 无法判断 | 无法判断 | ✅ | ⚠️ 只在工具写了一轮结束的记录时 | 无法判断 | ⚠️ 只在 Qwen Code 写了一轮的结果记录时 |
| 出错中断 | ❌ 文件里没有出错的记号，显示为“跑完了” | 无法判断 | 无法判断 | ✅ 出错、被中止、中断 | ⚠️ 只在结束记录带错误时 | 无法判断 | ⚠️ 出错、被取消；同样只在写了结果记录时 |
| 卡住了 | ✅ | 无法判断 | 无法判断 | ✅ | 写了结束记录时 ✅；没写时会话一直是运行中，停下超过阈值就显示为“卡住了” | 无法判断 | 同 WorkBuddy、CodeBuddy |

Grok、Copilot CLI、豆包分不清“跑完了”和“还在跑”。它们的会话不进列表，只在页面底部计数为“无法判断状态的 N 个”，可以展开看是哪些。

**与通知的差别**

同一个会话，页面和通知对它的说法应当一致。已知的例外：

- 中断之后马上又提了新问题（会话没有停下），新的这一轮正常结束：通知把这整段运行算作出错，发“出错中断”；页面看最近一个提问之后的那一轮，显示“跑完了”。
- 出错之后只有子代理还在动，主线上没有新的步骤：页面仍是“出错中断”（只看主线）；通知把子代理带来的这段运行当作新的一轮，结束时可能发“跑完了”。
- 主线上没有提问的会话：通知照常，页面不列。
- Grok、Copilot CLI、豆包：页面只计数（见上）；通知照“通知”一节的表。
- 通知不补发服务重启前、导入历史时的事，也有“最短时长”；页面没有这些限制，重启后、导入的历史里该列的照样列出（超过时限的在“已移出的”里）。

升级到有这一页的版本后，第一次启动要先给数据库建索引，见“数据库的大小与整理”。

## Hooks（可选）

不装 hooks 也能用：服务只靠 transcript 就能工作。区别是：

- 没有 hooks：无法显示“等待权限确认”，状态更新会稍慢（取决于 transcript 写入；文件监听之外，最近活跃会话的文件每 3 秒复查一次，整个目录每 60 秒完整扫描一次）。
- 有 hooks：状态接近实时。

服务理解全部 14 个事件：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PermissionDenied`、`PostToolUse`、`PostToolUseFailure`、`SubagentStart`、`SubagentStop`、`Notification`、`Stop`、`StopFailure`、`PostCompact`、`SessionEnd`。每个事件一条 HTTP hook，指向 `http://127.0.0.1:4317/hooks`，超时 2 秒，不设 `matcher`。

### 安装与移除（推荐）

先构建（`pnpm build`），然后：

```
node packages/server/dist/cli.js hooks install
node packages/server/dist/cli.js hooks uninstall
```

- 可选参数：`--port <n>`（hook 指向的端口，默认 4317）、`--yes`（不询问直接写入）、`--settings <文件>`（要修改的 settings 文件，默认 `~/.claude/settings.json`，也可用环境变量 `AGENT_CANVAS_SETTINGS_FILE` 指定）。
- 写入前会列出 settings 文件路径、hook 地址、将要添加（或移除）的事件和备份文件名，并询问是否继续；输入 `y` 才写入。在非交互终端（脚本、管道）里必须加 `--yes`，否则不做任何改动并以退出码 1 退出。
- 原文件存在时，先复制一份备份 `settings.json.bak-agent-canvas-<YYYYMMDD-HHMMSS>`（同名已存在时加序号，不覆盖已有备份），再写入。
- install 只追加：缺的事件加上，已有事件的数组末尾追加一项，不改动、不删除已有的条目和其他设置；已经全部装好时不写文件。uninstall 只移除 url 指向本端口 `/hooks` 的条目。写回时保留原文件的 BOM、换行符（CRLF / LF）和缩进。
- 遇到不寻常的文件会拒绝写入，原文件保持不变（退出码 1）：不是合法 JSON、顶层不是对象、`hooks` 的形状不对、指向不存在目标的符号链接、含有 JSON 读写后会变的数字（例如超过 2^53 的整数）、重复的键或读写后会被重新排序的键（例如与其他键混在一起的 "0"、"10" 这类整数键）、确认期间文件被别的程序修改。
- 改了服务端口时，install 和 uninstall 都要带上同一个 `--port`，例如 `hooks install --port 4400`。
- 写入后，新开的 Claude Code 会话才会使用这些 hooks。

### 手动合并到 `~/.claude/settings.json`（备选）

1. 先备份：复制 `~/.claude/settings.json` 为 `settings.json.bak`。
2. 打开 [`docs/hooks-snippet.json`](./hooks-snippet.json)，把其中 `hooks` 下的每个事件合并进 settings.json 顶层的 `"hooks"` 键：
   - settings.json 里没有 `hooks` 键：直接把整个 `hooks` 对象粘贴为顶层键。
   - 已有 `hooks` 键，但没有某个事件：加上该事件及其数组。
   - 某个事件已有数组：把本片段的那一项（`{ "hooks": [ { "type": "http", ... } ] }`）追加到现有数组里，不要替换原有条目。
3. 保存后，新开的 Claude Code 会话会使用这些 hooks。

手动移除：删除你合并进去的这些条目（url 为 `http://127.0.0.1:4317/hooks` 的那些），或用备份文件覆盖回去。手动合并时如果用 `--port` 改了端口，必须把每条 hook 的 url 改成相同端口，例如 `http://127.0.0.1:4400/hooks`。

### 失败行为

agent-canvas 没有运行时，HTTP hook 连接失败会立刻报错，而 Claude Code 把它当作不阻塞的错误，继续正常工作，不受影响。超时设为 2 秒也是为了避免服务卡住时拖慢 Claude Code（HTTP hook 默认超时是 600 秒）。

## 诊断页

页面右上角的“诊断”打开 `#/diagnostics`（<http://127.0.0.1:4317/#/diagnostics>），每 5 秒自动刷新，内容来自 `GET /api/diagnostics`：

- 服务：是否正在导入、推导规则版本、数据库标识。
- 数据库：文件大小；数据库整理（压缩旧数据）的进度；回收空间是否完成，被跳过时说明原因和补救办法；检索索引是已建好、正在建（已建 / 总数）还是失败（下次启动自动重试）；有损坏的数据时给出条数。详见下文“数据库的大小与整理”。
- Hooks：是否收到过 hook、最近一次收到的时间（超过 10 分钟没有收到时提示）；每个事件收到的次数和最近一次的时间；以及 14 个事件中哪些从未收到过（装了 hooks 但某些事件一直没出现，通常只是还没有触发它的操作，例如 `PermissionDenied`）。Codex 会话目录存在（即使还没有 Codex 会话）或有 Codex 数据时按来源分成 Claude Code 和 Codex 两部分（只装了 Claude Code 的机器上不出现 Codex）；Codex 一栏先显示一行 Codex 会话目录及它是否存在，再按它自己的 11 个事件计算从未收到的事件；一个 Codex hook 都没收到时提示 Codex hooks 尚未安装或尚未在 Codex 里确认信任。
- Hooks 一栏的最后一行是“被丢弃的外来 hook 调用”：自服务启动以来（重启后归零），Grok、Copilot CLI 调用了为 Claude Code / Cursor 安装的 hook、被服务认出并丢弃的次数（见“钩子串扰”）。
- Gemini CLI、Grok、Copilot CLI、DeepSeek、WorkBuddy、CodeBuddy、豆包、Qwen Code：目录存在、已有会话或读到未识别记录时，各有一栏：读取的目录及它是否存在（目录在服务启动之后才出现时显示“存在，但……尚未读取”，重启服务后读取）、会话数、该来源的未识别记录（类型以 `gemini:`、`grok:`、`copilot:`、`deepseek:`、`workbuddy:`、`codebuddy:`、`doubao:`、`qwen:` 开头，同样也列在下面的总表里）。这些来源未经真实数据核对，显示不对时先看这里。后五个来源的一栏按情况多出几行：
  - 有几个读取的目录时（WorkBuddy 的两个根、豆包的两个变体）：“读取的目录 1：……（存在 / 不存在）”逐个列出。
  - DeepSeek：“有其他格式版本文件（不读）的会话目录：N 个”；Node 不支持解压时，目录行写“存在，但无法读取，原因见下”，下面一行警告“无法读取：需要 Node 22.15 或更高”。
  - WorkBuddy、CodeBuddy、豆包、Qwen Code：“在另一个目录或配置里重复出现、只读了一份的会话：N 个”（Qwen Code 是同一个会话 id 出现在两个项目目录下）。
  - 豆包：“时间只能取自文件修改时间的线程：N 个”“没有主代理或有多个主代理、没有读取的对话：N 个”。
  - Qwen Code：“托管会话（格式不支持，没有读取）：N 个”，为 0 时也显示；不为 0 时显示为警告。
- 导入失败：读取或处理失败的文件、错误信息和时间。
- 未识别的记录类型：每种类型的次数和一条样例（样例可能含对话内容，展开后才显示）。
- 文件读取进度：已记录的文件总数和尚未读完的文件（已读 / 总字节）。Codex 文件的路径以 `codex:` 开头，前面带 Codex 标记（导入失败一节同样）。

## rebuild

```
node packages/server/dist/cli.js rebuild
```

它根据数据库里保存的原始事件重新推导出图相关的表，进度打印到 stderr，成功时打印 `agent-canvas rebuild complete`。通常不需要手动运行：升级后 `start` 会按需自动重建。它与运行中的服务共用锁文件，服务在运行时会以“already running”报错退出，先停止服务再运行。

## 数据库的大小与整理

数据库里最占地方的是原始记录（用于重建）和每一步的详情（工具的输入输出、回复全文）。这两样都压缩存放，读的时候解压，不丢任何数据。

**从旧版本升级后的第一次启动**会在后台做三件事，期间页面照常可用，进度在诊断页的“数据库”一栏：

1. 把已有的数据改写成压缩形式（分批进行，中途停掉服务也没关系，下次启动接着做）。
2. 回收空间（`VACUUM`），数据库文件到这一步才真正变小。它需要大约等于数据库大小的临时磁盘空间；空间不够时会跳过并在诊断页说明——数据已经压缩好了，只是文件暂时没变小。回收的那一小段时间里新记录排队等待，不会丢。
3. 建检索索引。建好之前检索结果可能不全，页面会提示。

压缩和建索引期间，磁盘上临时多出的日志文件（`data.db-wal`）不到 100 MB，与数据库大小无关；只有回收空间那一步需要上面说的大块临时空间。2026-11-13 在一份真实数据上测得（一次测量，不是保证）：2,571 MB 的数据库升级后是 1,460 MB，整个过程约两分钟。

**手动整理**：回收空间被跳过（腾出磁盘空间之后），或者想确认都整理完了，停掉服务后运行：

```
agent-canvas compact          # 从源码运行时：node packages/server/dist/cli.js compact
```

它做完剩下的压缩并回收空间，打印前后的文件大小。加 `--force` 表示即使之前记录为已完成也再回收一次。服务在运行时它会以“already running”报错退出。

**升级到支持 Gemini CLI、Grok、Copilot CLI 的版本后的第一次启动**会先给数据库建一个索引（按边的目标节点，删除节点时用），一次性的，每一百万条边约 1–2 秒，建好之后服务才开始工作；以后的启动不再需要。这个索引此后一直存在，对所有来源（包括 Claude Code、Codex、Cursor）都有代价：边的表约大 84%（一次测量：22 万条边，表 30.9 MB，索引 25.8 MB），写入边约慢 2.2 倍（主要影响首次导入和重建）。这是换来“回退时快速删除节点”的代价；目前只有 Gemini CLI 和 Grok 的回退会删除节点。

**升级到有“待处理”页的版本后的第一次启动**会先给数据库建三个索引（待处理页按会话取最近的步骤和 hooks 用），一次性的，开始时打印一行 `agent-canvas indexing stored records for the attention page (one-time)…`。在一个 2 GB 的自造数据库上测得约 8 秒（一次测量，不是保证），建好之前服务还没开始工作，页面打不开，这期间 hooks 发来的事件和服务没在运行时一样被丢弃；以后的启动不再需要。`rebuild` 和 `compact` 打开还没有这些索引的数据库时同样先建，并打印同一行提示。这三个索引此后一直存在，对所有来源都有代价：数据库约大 1.5%（一次测量：1.3 GB 的数据库多 19 MB），写入步骤约慢 6%（主要影响首次导入和重建）。

**升级前建议备份**：停掉服务，把数据目录里的 `data.db`（连同旁边的 `data.db-wal`、`data.db-shm`，如果有）复制到别处。

**不能降级**：新版本的数据库旧版本打不开（旧版本会在启动时直接报错退出，不会读错或写坏）。要退回旧版本，停掉服务，把升级前备份的文件放回数据目录。

## 安全说明

- 只监听 `127.0.0.1`，不对局域网开放。
- 没有任何认证。为防止网页跨站访问，`Host` 或 `Origin` 不是回环地址的请求会被拒绝（`/hooks` 仍返回空的 200，但内容不会被采纳）。
- 数据库含有你的对话和工具输出的明文，请像对待对话记录本身一样对待数据目录（不要同步到云盘、不要分享）。
- 服务对 transcript 只读；使用默认数据目录（`~/.agent-canvas`）时，服务不会往 `~/.claude` 下写任何东西（若把 `AGENT_CANVAS_DATA_DIR` 设到 `~/.claude` 之下，数据库和锁文件当然会写在那里）。只有你运行 `hooks install` / `hooks uninstall` 时才会修改 settings 文件（并先备份）。

## 状态与错误在哪里看

- 会话状态：运行中、等待输入、等待权限确认、空闲、已结束。一个“运行中”的会话超过 15 分钟没有任何活动时，页面显示为“长时间无活动”（例如 Claude Code 进程被杀、API 报错后没有后续记录）；它不计入项目的活跃会话数，一有新活动就恢复。
- 错误：读不了的文件、写库失败、hook 处理失败会写到服务的 stderr（每个文件每分钟最多一行，只含路径和错误信息，不含对话内容），并出现在诊断页的“导入失败”和 `GET /api/diagnostics` 的 `ingestFailures` 里。诊断接口还给出未识别的记录类型、最近一次收到 hook 的时间和各事件的次数、各文件读取进度、`importing`、推导规则版本 `normalizerVersion` 和数据库标识 `dbEpoch`。

## 已知限制

- 在一份真实数据上，只有约 3% 的思考节点带文本（6,352 个中的 217 个），其余只有时长，所以因果链主要依靠回复文本和思考时长。
- transcript 格式不是稳定的契约：无法识别的记录类型会被计数，可在诊断页或 `GET /api/diagnostics` 查看。
- 等待权限确认的工具会一直保持该状态，直到它的结果到达。
- 复盘时，抽屉里显示的是节点现在的内容（例如工具最终的输出），不是所选时刻的内容。
- 复盘不重现“等待权限确认”的过程：一个节点在结束之前一律显示为执行中。
- Windows 是经过测试的平台。
- 后台派出的子代理：派发节点在子代理真正结束时才结算，耗时是从派出到结束。结束信号有：主线收到的任务通知（同时给出成功或失败）、SubagentStop hook、子代理记录里的 end_turn / 交回调用 / 中断。多个信号以任意先后到达结果都一样：有失败信号就记为失败并取失败的时间，否则取最早的时间。没有自己的结束信号时：同一个子代理之后又被后台派出过，就算在那次派出开始时结束；否则派出之后会话结束过，就记为失败（之后恢复会话也不会让它回来，原来的进程已经没了），都不是则保持“执行中”。同一个子代理被后台派出多次时，每次派出只认自己时间段里的信号。
- 以上信号都没有、会话也没有结束时（例如进程被直接杀掉），派发节点的状态仍是“执行中”。主线不再推进时（会话已结束、空闲、等待输入，或运行中但超过 15 分钟没有动静），主线上仍在执行的步骤显示为“未结束”；后台工作（子代理的步骤和派发节点）多留 5 分钟：只要会话没结束、最近 5 分钟内还有记录，就仍算在进行，因为主线空闲时后台子代理可能还在工作。复盘视角显示的是历史，不受此影响。显示为“未结束”时，画布、瀑布图和详情抽屉都用虚线、无动效的样式，不再声称正在进行。

- Cursor：数据库的格式没有公开文档，是按实际观察到的形状读的；Cursor 升级后可能出现未识别的记录（诊断页的 Cursor 一栏可见），需要跟着更新。
- Cursor：没有“等待权限确认”状态；思考内容只有 Cursor 存下来的那部分文本；不显示 token 用量。
- Cursor：一条记录的内容改回到和之前某一版完全相同时，不会再存一次；重建后该节点停在中间那一版，直到它下一次变化。
- Cursor hooks 的载荷字段和 Windows 上的调用方式取自官方文档，还没有用真实的 Cursor 核对过。
- Cursor：会话很长（上万步）时，第一次导入需要一段时间，在后台进行。
- Gemini CLI、Grok、Copilot CLI：读法按公开资料写成，**未经真实数据核对**；各自的限制见上文“Gemini CLI、Grok、Copilot CLI”一节。
- DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作：同样按公开资料写成，**未经真实数据核对**（DeepSeek Harness 用一个真实会话核对过，范围见该节开头）；DeepSeek 只读第 4 版文件且需要 Node 22.15 或更高，WorkBuddy / CodeBuddy 只显示当前分支，豆包没有用量、模型、思考和工作目录。详见上文“DeepSeek Harness、WorkBuddy、CodeBuddy Code、豆包工作”一节。
- Qwen Code：按 `v0.27.4` 的开源代码写成，**未经真实数据核对**；只显示当前分支，托管会话和 0.4.0 以前的文件不读，`/branch` 复制出来的会话跨会话相加时用量重复。详见上文“Qwen Code”一节。
