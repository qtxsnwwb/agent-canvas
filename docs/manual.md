# agent-canvas 使用手册

> 这里是完整的参考说明。想快速上手请看[项目首页](../README.md)。

agent-canvas 是一个本地服务：它读取 Claude Code 的 transcript 文件、OpenAI Codex 的会话文件和 Cursor 的本地数据库，并接收 hook 事件，在固定的本地网址上用网页展示每个会话正在做什么。两种工具的会话用同一套页面展示（Codex 见下文“Codex”）。
每个会话显示为一张实时更新的画布。默认的“概览”视角只画骨架（每个轮次一张卡片，下面挂它派出的子代理），选中一个轮次或子代理，它的执行过程在下方以瀑布图列出。另有逐步、拓扑、因果、复盘四个视角（见下文“画布”）。首页可以检索会话，诊断页给出服务和 hooks 的运行情况。

## 从 claude-canvas 升级

这个项目原名 claude-canvas，接入 Codex 和 Cursor 之后改名为 Agent Canvas。新版本**不认任何旧名字**，从旧版本升级时需要手动做一次：

1. 停掉旧服务。
2. 数据目录改名：把 `~/.claude-canvas` 改成 `~/.agent-canvas`（不改的话新版本会从空库开始，重新导入全部会话）。
3. 环境变量改名：`CLAUDE_CANVAS_*` 一律改成 `AGENT_CANVAS_*`，名字的其余部分不变。
4. 如果移动或改名了项目文件夹：Codex 和 Cursor 的 hooks 里写的是 `cli.js` 的绝对路径，需要在旧位置先 `hooks uninstall --codex` / `--cursor`，再在新位置重新安装（Codex 还要重新确认信任）。Claude Code 的 hooks 指向的是端口地址，不受影响。
5. 浏览器里记住的首页筛选和精简模式会回到默认值，重新选一次即可。

## 环境要求

- Node ≥ 22
- pnpm（可选：没有全局安装时用 `npx --yes pnpm@10` 代替 `pnpm`）

## 安装、构建、启动

已安装 pnpm：

```
pnpm install
pnpm build
pnpm start
```

未安装 pnpm：

```
npx --yes pnpm@10 install
npx --yes pnpm@10 build
npx --yes pnpm@10 start
```

启动后终端会打印：

```
agent-canvas listening on http://127.0.0.1:4317
```

在浏览器打开 <http://127.0.0.1:4317> 即可。按 Ctrl+C（SIGINT）停止服务。

换端口：`pnpm start --port 4400`（或直接 `node packages/server/dist/cli.js start --port 4400`），打印的地址会随之变化。

首次启动会导入 `~/.claude/projects` 下全部已有的 transcript；历史很多时需要一段时间，导入在后台进行，页面在此期间已可使用（`GET /api/diagnostics` 的 `importing` 为 `true`，诊断页上显示“正在导入：是”）。在一份真实数据上测得（340 MB、612 个文件）：导入约 2 分钟，导入完成后数据库约为 transcript 总量的 1.6 倍；导入期间 WAL 文件会临时增长到 transcript 总量的数倍，之后收缩到 64 MB 以内，请为数据目录预留空间。之后服务会持续监视 transcript 的变化。

同一个数据目录只能运行一个服务：启动时会创建锁文件 `<数据目录>/agent-canvas.lock`（记录 pid 和启动时间）。若已有服务在运行，第二次 `start` 会打印 `agent-canvas is already running with this data directory (pid N); lock file: …` 并以退出码 1 退出。上一次进程异常退出留下的锁会被自动接管。

升级 agent-canvas 后，如果推导规则的版本变了（或上次重建被中断），`start` 会在开始监听前自动重建派生数据，先打印 `agent-canvas rebuilding derived data (reason: …)`，再打印正常的监听地址。2026-11-10 在一份真实数据上测得：升级时有 14 个会话被自动重新推导（这是一次测量，不是保证）。

## 首页与检索

首页按项目列出会话，项目内按最近活动时间排序。

- 项目名：取该项目下会话的工作目录中，编码后（非字母数字字符换成 `-`）与项目目录名相同的那个；找不到时显示项目目录名本身。
- 会话标题按以下优先级取第一个有的：自定义标题（`/rename` 等写入的 custom title）> agent 名称 > hook 提供的标题 > 第一条提示（去掉首尾空白、换行折成空格，取前 60 个字符）。

顶部的检索框：

- 检索范围：会话标题、会话 id、分支、工作目录，以及每条主线程提示的前 200 个字符。
- 不检索：工具输出、回复文本、子代理里的提示。
- 至少输入 2 个字符才开始检索；查询最多取前 200 个字符。
- 按字面匹配：不支持通配符或正则，只有 ASCII 字母不区分大小写（`É` 和 `é` 视为不同字符）。命中处在结果里高亮，每个会话最多列出 3 处命中，点结果打开该会话。
- 2026-11-10 在一份真实数据上测得：一次检索在几毫秒内返回（测量值，不是保证）。

## 画布

### 概览（默认）

- 画布上每个轮次是一张卡片：提示内容、工具调用次数、历时、失败数；正在进行的轮次带呼吸动效，并显示“正在执行 <工具名>”。轮次派出的子代理是挂在卡片下面的节点，子代理里再派出的子代理挂在它下面。
- 画布下方是“执行过程”面板（瀑布图）：每一步一行，按开始时间排列，右侧横条画在同一条时间轴上，长度就是耗时，并行的步骤在时间上重叠。没有时长的步骤（提示、回复）画成一个菱形标记。
  - 没有选中任何东西时，面板跟随最新的轮次；点画布上的轮次卡片或子代理节点，面板改为列出它的步骤；点画布空白处回到跟随最新。
  - 点一行，在右侧抽屉里看这一步的完整入参和输出；子代理那一行上的“内部步骤”切到那个子代理。
  - 打开一步之后，面板里导致这一步的那些步骤（沿连线往回直到本轮提示，子代理里的步骤会接到派出它的那一步）左侧带标记，其余变淡；其中这一步的“直接依据”（往回遇到的最近一段思考和回复，子代理里则是它的任务提示）用橙色底标出。抽屉顶部的“推理链”按时间顺序列出链上的思考和回复，直接依据带标签，点一行跳到那一步。
  - 会话已经停下（空闲、结束、长时间无活动）时，没有结束的步骤不再随时间变长，面板标题显示“有步骤未结束”。
  - 窗口较窄（不足 1100 像素）时，抽屉只盖住上面的画布，面板保持整行宽度。
  - 有步骤在执行时，面板每秒更新一次；滚动条在底部时会跟着新步骤往下走。
  - “精简”时面板不列没有内容的思考和普通系统记录，“完整”时全部列出。
- 点面板右上角的 × 关闭面板；再点任意轮次或子代理重新打开。

### 逐步及其他视角

以下说明针对把每一步都画成画布节点的“逐步”视角，以及在它基础上的拓扑、因果、复盘。

- 网格式自动布局：每个轮次（一次提示及其后的回复、工具调用）排成一块；轮次按时间从左到右排，一行排满（约四张大纲卡片的宽度）就换行，行与行之间有一条回折线把上一行末尾连到下一行开头。轮次内部的步骤自上而下排，超过约一屏高时折成并排的几列（分叉到汇合的一段不拆开）；并行的工具调用左右排开。画布不会随着会话变长而一直往下延伸。
- 状态颜色：执行中为蓝色、等待权限确认为橙色（两者带呼吸动效），成功为绿色、失败为红色、被拒绝为深红色；没有状态的节点按类型着色（提示为紫色）。
- 默认是“精简”显示（会话页右上角的“精简 / 完整”开关，选择会记在这个浏览器里）：
  - 没有记录内容的思考节点不单独画，它的耗时显示在后面那个节点上（“思考 3.2s”，不足 1 秒不显示）；有内容的思考节点、以及正在进行的最后一个思考节点照常显示。
  - 系统节点不画，上下文压缩和用户中断除外。
  - 同一个轮次、同一条线程里连续 3 次及以上成功的同一种工具调用（先后发生的，或同一步并行发出的）合并成一个节点，如“Read ×5”；点它展开成各次调用，之后保持展开。失败、被拒绝、仍在执行的调用不合并。停止跟随期间不会形成新的合并节点。
  - 切到“完整”则每条记录都画成一个节点。在一组真实数据上，精简后节点数从 24,068 降到 11,696。
- 默认只展开最后 3 个轮次，更早的轮次各折叠成一个摘要节点（节点数、工具调用数、耗时、失败数）。点摘要节点（或其中的“展开”）展开该轮次，点轮次标题栏上的“折叠”把它折回去。
- 一个轮次很长时（超过 60 个节点），只显示它的提示和最后 40 个节点，中间的折叠成“更早的 N 个节点”；点其中的“展开全部”显示整个轮次。仍在执行或等待权限确认的节点不会被折叠进去。
- 画布会跟随最新的节点，直到你平移、缩放或展开 / 折叠了什么；不跟随时右下角出现“回到最新”，点它恢复跟随。停止跟随后，新轮次到来时也不会自动折叠已展开的轮次，以免内容在你阅读时移动。
- 点一个节点（或用 Tab 聚焦后按 Enter / 空格）在右侧抽屉里查看它的完整内容：文本、入参、输出和原始记录；按 Esc 或 × 关闭。
- 子代理默认收起为单个节点（带内部节点数）；点节点上的“展开”把它展开成一个容器，里面按同样的规则排布它的内部节点，再点“收起”收回去。子代理里派发的子代理也能在容器里继续展开（嵌套）。一个子代理的内部节点很多时（超过 60 个），和长轮次一样只显示它的第一个节点和最后 40 个，中间的折叠成“更早的 N 个节点”，点“展开全部”显示全部。
- 信息栏右侧可以切换视角：
  - 逐步：全部节点，子代理可以展开。
  - 拓扑：隐藏思考和回复节点，只看提示、工具调用和子代理（子代理一律收起），被隐藏节点两侧的连线接到一起，链路不断开。
  - 因果：节点和逐步视角相同，思考节点放大显示它的内容（没有记录内容时显示时长）。选中一个节点后，从它沿连线往上直到本轮提示的那条链被高亮，其余变暗；抽屉里的“推理链”按时间顺序列出链上的思考和回复，点其中一行选中那个节点。链被折叠截断时，抽屉里会提示“更早的部分已折叠”，点“展开”展开截断它的轮次或节点。在因果视角选中节点会停止跟随，链上的内容不会在阅读时被折叠走。
  - 复盘：把会话回放到过去的某一时刻，见下一节。
- 2026-11-10 在一份真实数据上测得：最大的会话（约 7,500 个节点）从打开到画出画布约 1 秒（测量值，不是保证）。

### 复盘

复盘视角在画布下方显示一条时间轴，范围从会话最早的节点开始，到最晚的节点开始或结束为止：

- 播放 / 暂停，倍速 1× / 10× / 60×；播放到末尾自动停止，在末尾再点播放从头开始。“回到末尾”直接跳到最后。
- 拖动滑块选择时刻；滑块上方每个轮次一个刻度，点刻度跳到该轮次开始。滑块获得焦点时，PageUp / PageDown 跳到上一个 / 下一个轮次（刻度本身不参与 Tab 切换）。
- 时间轴显示当前时刻（回放范围跨了日期时带上 `MM-DD`）和“第 N / M 轮”。
- 画布只显示该时刻及之前出现的节点，之后的隐藏；在该时刻还在执行中的工具显示为执行中。
- 工具和子代理节点下方多一行耗时和 token（输入 / 输出），回复节点只显示 token；时间轴右侧是到该时刻为止的节点数和 token 合计，同一条消息拆成的多个节点只计一次。
- 历史会话里工具的耗时由开始和结束时间推算（hook 提供了 `duration_ms` 时用 hook 的值）。

## Codex

- 服务启动时会自动读取 `~/.codex/sessions` 下的 Codex 会话文件（Codex 桌面应用和 CLI 写的都是这里），并持续监视。目录不存在时跳过，不报错。
- 用环境变量 `AGENT_CANVAS_CODEX_DIR` 指定别的目录；设为空字符串表示不读取 Codex。
- 会话标题取自 `~/.codex/session_index.jsonl`（Codex 给会话起的名字），没有时取第一条提示。
- 同一个工作目录下的 Claude Code 会话和 Codex 会话属于同一个项目。
- 首页会话卡片、检索结果和会话页信息栏上标明来源（Claude Code 或 Codex）。两种来源都有的项目，项目卡片上有两个小标记。
- 有 Codex 会话时，首页项目列表上方出现“全部 / Claude Code / Codex”筛选，选择记在这个浏览器里。筛选后没有该来源会话的项目不显示；地址里指定的项目即使被筛掉也照常显示。服务给出的项目会话数不分来源，所以筛选时，同时有两种来源的项目不显示会话数，顶部只在数字准确时显示会话总数和进行中的数量。
- Codex 的子代理是单独的线程，显示为派出它的那一步下面的子代理，展开后是它内部的步骤。

### Codex hooks（可选）

不装 hooks 也能用：服务靠监视会话文件得到 Codex 会话，延迟几秒。装上后多了两样，接近实时（1 秒内）：会话状态的变化（开始运行、结束、已退出），以及等待权限确认（会话显示“等待权限确认”，该轮次里最新一个还在执行的工具节点也显示等待确认）。hooks 不新建节点，也不决定节点的结果：步骤一律来自会话文件，所以工具节点并不会因为装了 hooks 而更早出现；除了等待权限确认期间那个临时的“等待确认”标记，有没有 hooks 画出来的图完全一样。

Codex 的 hook 只能运行命令，不能直接发 HTTP，所以 agent-canvas 提供一个转发命令：`node <agent-canvas>/packages/server/dist/cli.js hook-forward --origin codex --port 4317`。它从标准输入读 Codex 给的 JSON，原样发给本机服务的 `/hooks?origin=codex`，然后退出。

安装与移除（流程和 Claude Code 的 hooks 一样：先列出改动、确认、备份、只追加）：

```bash
node packages/server/dist/cli.js hooks install --codex      # 写入 ~/.codex/hooks.json（不存在时新建）
node packages/server/dist/cli.js hooks uninstall --codex    # 只移除本安装、本端口的那几条
```

- 写入 11 个事件：`SessionStart`、`SessionEnd`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`SubagentStart`、`SubagentStop`、`Stop`、`PostCompact`、`Interrupt`。每条都是 `async: true`（后台运行，不改变 Codex 的结果），`command` 和 `commandWindows` 都写，用绝对路径指向当前的 `node` 和这份 `cli.js`。超时：`SessionEnd`、`Interrupt` 是 3 秒（Codex 对这两个事件最多允许 3 秒），其余 5 秒。
- 选项和 Claude Code 的一样：`--port <n>`、`--yes`（非交互终端必须加）、`--settings <file>`（写别的文件）；环境变量 `AGENT_CANVAS_CODEX_HOOKS_FILE` 改默认路径。`~/.codex` 目录不存在时视为没装 Codex，不做任何改动。
- **装完要在 Codex 里确认信任这些 hooks 才会运行**：桌面应用在“设置 → Hooks”，CLI 里输入 `/hooks`。没确认时 agent-canvas 只靠会话文件工作，诊断页的 Codex 一栏会显示“尚未收到 Codex 的 hook”。
- Codex 的信任绑定在 hook 的内容上。移动或升级 agent-canvas 后命令里的路径会变：先 `hooks uninstall --codex`（在旧位置运行）或手动删掉旧的几条，再在新位置 `hooks install --codex`，并重新确认信任。
- 换了 node（例如用 nvm / fnm 升级后旧路径失效）时，再运行一次 `hooks install --codex`：它认得出本安装的旧条目、说明它们已过期，并在同一次写入里换成当前 `node` 的命令（之后同样要在 Codex 里重新确认信任）。判断“本安装的条目”时按命令解析出 `cli.js` 的路径比较（Windows 上不分大小写），端口写成 `--port 4317`、`--port=4317` 或不写（默认 4317）都认。
- 失败行为：转发命令永远以退出码 0 结束、不输出任何内容、不读写文件；服务没启动时立刻退出（连接被拒），服务不回应时 1 秒后放弃。Codex 的行为不受影响。每个 hook 事件会启动一次 node（本机实测转发命令从启动到退出约 0.25 秒，和空跑 `node` 差不多）。大多数事件因为是 `async` 在后台运行，不拖慢 Codex；但 `SessionEnd`（以及 `Interrupt`）即使写了 `async: true`，Codex 也同步运行它，所以退出（或打断）时会多等一次转发：通常约 0.25 秒，服务卡住时最多约 1.3 秒（转发命令自己的 1 秒上限加启动），无论如何不超过 3 秒的超时。
- hooks 只给出会话状态和权限等待，节点、状态、开始和结束时间都以会话文件为准。会话状态由会话文件里主线程的轮次和 hook 留下的标记一起算出，与两者到达的先后无关：子代理线程的 hook（带 `agent_id`，或它的轮次已在会话文件里归到子线程）不会把已经结束的会话改回运行中；同一轮次在 `Stop` 之后又收到 `UserPromptSubmit` 或 `PermissionRequest`，说明这一轮还在继续，会重新算作运行中；`Stop` 先于或晚于会话文件里的轮次结束到达，结果一样。

已知限制：

- 思考内容：Codex 的思考正文是加密的，只有摘要，而且摘要多数为空。Codex 会话的“因果”视角主要靠回复文本。
- token：不显示 Codex 的 token 用量，复盘视角里 Codex 会话的 token 合计为 0。
- 已归档会话（`~/.codex/archived_sessions`）不导入。归档一个会话后，它在这里显示为“源文件已删除”，已采集的内容仍可看。
- Codex 的会话文件格式不是稳定接口，升级 Codex 后可能出现未识别的记录，可在诊断页查看。
- Codex 自己发起的审批复核线程（不是由某次工具调用派出的）不显示。
- Codex hooks 需要使用者在 Codex 里手动确认信任，改动或重新安装后要再确认一次；没确认时只靠会话文件，延迟几秒。
- Codex hook 载荷的字段取自官方文档，还没有用真实载荷核对过（尤其是 `turn_id` 是否和会话文件里的轮次 id 一致、子代理里的 hook 带什么 `session_id` / `agent_id`，以及 Windows 上 `commandWindows` 由哪个 shell 执行）。所以第一版的 hooks 不建节点（例如在 `exec` 里跑的命令，hook 报的工具名和 id 都可能和会话文件里的调用对不上）；录到真实载荷后再考虑让 hooks 提前显示工具节点。
- 权限确认之后到工具结束之前没有 hook，所以批准后那个工具节点和会话会一直显示“等待权限确认”，直到该轮次的下一个 hook（例如工具结束的 `PostToolUse`）或会话文件里该轮次的调用都结束。权限请求不带工具调用的 id，显示等待的是该轮次里最新一个还在执行的工具节点，并行调用时可能不是真正在等的那个。
- 派发子代理的调用找不到对应的子代理线程时（例如派出失败），派发节点在派出它的轮次进行中显示执行中，轮次结束后显示失败；之后子代理线程出现，就改为跟着它走。
- 追加给子代理的任务（`followup_task`、`send_message`），在逐步视角的因果链上接在子代理上一个任务的回复之后，而不是接在发出追加任务的那次调用上。

## Cursor

- 服务启动时会自动只读地打开 Cursor 的本地状态数据库，并每 3 秒查一次哪些会话变了。数据库不存在时视为没装 Cursor，跳过，不报错。
  - 默认位置：Windows `%APPDATA%\Cursor\User\globalStorage\state.vscdb`；macOS `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`；Linux `~/.config/Cursor/User/globalStorage/state.vscdb`。
  - 用环境变量 `AGENT_CANVAS_CURSOR_DB` 指定别的位置；设为空字符串表示不读取 Cursor。
- 对 Cursor 没有影响：数据库以只读方式打开，只做按主键的短查询，不写入、不持有长事务；数据库被占用或出错时这一轮放弃，下一轮重试，错误显示在诊断页。
- 读到的记录会裁剪后存进 agent-canvas 自己的数据库（文本、工具参数、工具结果各截到 64 KB）。之后的重建只用这份记录，不需要再读 Cursor 的数据库；Cursor 归档或删掉会话后，已采集的内容仍可看。
- 导入范围：未归档、至少有一条消息的 Agent 会话。**不导入**：已归档会话、没发过消息的空会话、云端 / 后台 Agent、Tab 补全。会话在 Cursor 里被归档或删除后，这里显示为“源文件已删除”。
- 子代理：Cursor 的子代理是单独的会话，这里显示在派出它的那一步（`task_v2`）下面，展开后是它内部的步骤。从同一个会话分叉出来的两个会话各自显示它们共用的子代理。
- 项目归属：按会话的工作目录归到项目，和同目录的 Claude Code、Codex 会话在同一个项目下；取不到工作目录时归到“Cursor（未知目录）”。
- 会话标题取 Cursor 给会话起的名字，没有时取第一条提示。
- 每一步的状态：Cursor 记录的完成 → 成功；出错 → 失败；终端命令退出码不为 0 → 失败；被用户拒绝执行 → 已拒绝；已取消、所在轮次结束时仍未完成、会话被中止 → 失败（详情里注明原因）。
- 会话状态只有运行中和空闲；“已结束”只在装了 hooks 且 Cursor 发出会话结束事件时出现。超过 15 分钟没有活动的“运行中”显示为“长时间无活动”。
- 更新延迟：不装 hooks 时取决于轮询间隔和 Cursor 多久把内容写进数据库，通常几秒。

### Cursor hooks（可选）

不装也能用。装上后，“开始运行”和“一轮结束”在 1 秒内到达，并且每次事件会立即催一次读库。

```
node packages/server/dist/cli.js hooks install --cursor      # 写入 ~/.cursor/hooks.json（不存在时新建）
node packages/server/dist/cli.js hooks uninstall --cursor    # 只移除本安装、本端口的那几条
```

- 只装 5 个观察类事件：`sessionStart`、`beforeSubmitPrompt`、`stop`、`subagentStop`、`sessionEnd`。每条的形状是 `{ "command": "…", "timeout": 5 }`。
- **不装任何能拦住操作的 hook**。Cursor 的权限类 hook（`preToolUse`、`beforeShellExecution` 等）在转发程序输出异常时会阻止 Cursor 的动作，所以这里一个都不装。代价是 Cursor 会话没有“等待权限确认”状态，工具开始执行的时刻靠读库得到。
- 选项和另外两个工具的一样：`--port <n>`、`--yes`（非交互终端必须加）、`--settings <file>`；环境变量 `AGENT_CANVAS_CURSOR_HOOKS_FILE` 改默认路径。`~/.cursor` 目录不存在时视为没装 Cursor，不做任何改动。文件里已有 `version` 且不是 1 时拒绝写入。
- 命令用绝对路径指向当前的 `node` 和这份 `cli.js`。Windows 上 Cursor 用 PowerShell 执行，命令写成 `& "<node>" "<cli.js>" hook-forward --origin cursor --port <n>`；其他平台是普通命令行。
- Cursor 监视 `hooks.json`，保存后自动生效，不需要确认信任；没生效时重启 Cursor。
- **移动、升级或删除 agent-canvas 之前，先运行 `hooks uninstall --cursor`**。否则 hook 命令指向不存在的文件，每次触发都会报错；这种情况下 Cursor 是否照常继续，还没有用真实的 Cursor 验证过。换了 node 之后重新运行一次 `hooks install --cursor`，它会把过期的条目换成新的。
- 这些 hook 是同步的：每次触发 Cursor 会等转发命令结束（启动一次 node，约 0.25 秒，Windows 上再加 PowerShell 的启动时间；服务没响应时最多约 1.3 秒）。5 个事件每轮各触发至多一次。
- 转发命令永远以退出码 0 结束，不读写文件；只在 `beforeSubmitPrompt` 时向 Cursor 输出 `{"continue":true}`（明确放行），其他事件不输出。
- hooks 只给出会话状态，不建、不改节点；节点一律来自数据库。存下来的 hook 内容不含你的邮箱（载荷里的 `user_email` 会被去掉），但包含提示正文，和另外两个工具的 hook 一样。

## Hooks（可选）

不装 hooks 也能用：服务只靠 transcript 就能工作。区别是：

- 没有 hooks：无法显示“等待权限确认”，状态更新会稍慢（取决于 transcript 写入；文件监听之外，最近活跃会话的文件每 3 秒复查一次，整个目录每 60 秒完整扫描一次）。
- 有 hooks：状态接近实时。

服务理解全部 14 个事件：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PermissionDenied`、`PostToolUse`、`PostToolUseFailure`、`SubagentStart`、`SubagentStop`、`Notification`、`Stop`、`StopFailure`、`PostCompact`、`SessionEnd`。每个事件一条 HTTP hook，指向 `http://127.0.0.1:4317/hooks`，超时 2 秒，不设 `matcher`。

### 安装与移除（推荐）

先构建（`pnpm build`），然后：

```
node packages/server/dist/cli.js hooks install
node packages/server/dist/cli.js hooks uninstall
```

- 可选参数：`--port <n>`（hook 指向的端口，默认 4317）、`--yes`（不询问直接写入）、`--settings <文件>`（要修改的 settings 文件，默认 `~/.claude/settings.json`，也可用环境变量 `AGENT_CANVAS_SETTINGS_FILE` 指定）。
- 写入前会列出 settings 文件路径、hook 地址、将要添加（或移除）的事件和备份文件名，并询问是否继续；输入 `y` 才写入。在非交互终端（脚本、管道）里必须加 `--yes`，否则不做任何改动并以退出码 1 退出。
- 原文件存在时，先复制一份备份 `settings.json.bak-agent-canvas-<YYYYMMDD-HHMMSS>`（同名已存在时加序号，不覆盖已有备份），再写入。
- install 只追加：缺的事件加上，已有事件的数组末尾追加一项，不改动、不删除已有的条目和其他设置；已经全部装好时不写文件。uninstall 只移除 url 指向本端口 `/hooks` 的条目。写回时保留原文件的 BOM、换行符（CRLF / LF）和缩进。
- 遇到不寻常的文件会拒绝写入，原文件保持不变（退出码 1）：不是合法 JSON、顶层不是对象、`hooks` 的形状不对、指向不存在目标的符号链接、含有 JSON 读写后会变的数字（例如超过 2^53 的整数）、重复的键或读写后会被重新排序的键（例如与其他键混在一起的 "0"、"10" 这类整数键）、确认期间文件被别的程序修改。
- 改了服务端口时，install 和 uninstall 都要带上同一个 `--port`，例如 `hooks install --port 4400`。
- 写入后，新开的 Claude Code 会话才会使用这些 hooks。

### 手动合并到 `~/.claude/settings.json`（备选）

1. 先备份：复制 `~/.claude/settings.json` 为 `settings.json.bak`。
2. 打开 [`docs/hooks-snippet.json`](./hooks-snippet.json)，把其中 `hooks` 下的每个事件合并进 settings.json 顶层的 `"hooks"` 键：
   - settings.json 里没有 `hooks` 键：直接把整个 `hooks` 对象粘贴为顶层键。
   - 已有 `hooks` 键，但没有某个事件：加上该事件及其数组。
   - 某个事件已有数组：把本片段的那一项（`{ "hooks": [ { "type": "http", ... } ] }`）追加到现有数组里，不要替换原有条目。
3. 保存后，新开的 Claude Code 会话会使用这些 hooks。

手动移除：删除你合并进去的这些条目（url 为 `http://127.0.0.1:4317/hooks` 的那些），或用备份文件覆盖回去。手动合并时如果用 `--port` 改了端口，必须把每条 hook 的 url 改成相同端口，例如 `http://127.0.0.1:4400/hooks`。

### 失败行为

agent-canvas 没有运行时，HTTP hook 连接失败会立刻报错，而 Claude Code 把它当作不阻塞的错误，继续正常工作，不受影响。超时设为 2 秒也是为了避免服务卡住时拖慢 Claude Code（HTTP hook 默认超时是 600 秒）。

## 诊断页

页面右上角的“诊断”打开 `#/diagnostics`（<http://127.0.0.1:4317/#/diagnostics>），每 5 秒自动刷新，内容来自 `GET /api/diagnostics`：

- 服务：是否正在导入、推导规则版本、数据库标识。
- Hooks：是否收到过 hook、最近一次收到的时间（超过 10 分钟没有收到时提示）；每个事件收到的次数和最近一次的时间；以及 14 个事件中哪些从未收到过（装了 hooks 但某些事件一直没出现，通常只是还没有触发它的操作，例如 `PermissionDenied`）。Codex 会话目录存在（即使还没有 Codex 会话）或有 Codex 数据时按来源分成 Claude Code 和 Codex 两部分（只装了 Claude Code 的机器上不出现 Codex）；Codex 一栏先显示一行 Codex 会话目录及它是否存在，再按它自己的 11 个事件计算从未收到的事件；一个 Codex hook 都没收到时提示 Codex hooks 尚未安装或尚未在 Codex 里确认信任。
- 导入失败：读取或处理失败的文件、错误信息和时间。
- 未识别的记录类型：每种类型的次数和一条样例（样例可能含对话内容，展开后才显示）。
- 文件读取进度：已记录的文件总数和尚未读完的文件（已读 / 总字节）。Codex 文件的路径以 `codex:` 开头，前面带 Codex 标记（导入失败一节同样）。

## rebuild

```
node packages/server/dist/cli.js rebuild
```

它根据数据库里保存的原始事件重新推导出图相关的表，进度打印到 stderr，成功时打印 `agent-canvas rebuild complete`。通常不需要手动运行：升级后 `start` 会按需自动重建。它与运行中的服务共用锁文件，服务在运行时会以“already running”报错退出，先停止服务再运行。

## 安全说明

- 只监听 `127.0.0.1`，不对局域网开放。
- 没有任何认证。为防止网页跨站访问，`Host` 或 `Origin` 不是回环地址的请求会被拒绝（`/hooks` 仍返回空的 200，但内容不会被采纳）。
- 数据库含有你的对话和工具输出的明文，请像对待对话记录本身一样对待数据目录（不要同步到云盘、不要分享）。
- 服务对 transcript 只读；使用默认数据目录（`~/.agent-canvas`）时，服务不会往 `~/.claude` 下写任何东西（若把 `AGENT_CANVAS_DATA_DIR` 设到 `~/.claude` 之下，数据库和锁文件当然会写在那里）。只有你运行 `hooks install` / `hooks uninstall` 时才会修改 settings 文件（并先备份）。

## 状态与错误在哪里看

- 会话状态：运行中、等待输入、等待权限确认、空闲、已结束。一个“运行中”的会话超过 15 分钟没有任何活动时，页面显示为“长时间无活动”（例如 Claude Code 进程被杀、API 报错后没有后续记录）；它不计入项目的活跃会话数，一有新活动就恢复。
- 错误：读不了的文件、写库失败、hook 处理失败会写到服务的 stderr（每个文件每分钟最多一行，只含路径和错误信息，不含对话内容），并出现在诊断页的“导入失败”和 `GET /api/diagnostics` 的 `ingestFailures` 里。诊断接口还给出未识别的记录类型、最近一次收到 hook 的时间和各事件的次数、各文件读取进度、`importing`、推导规则版本 `normalizerVersion` 和数据库标识 `dbEpoch`。

## 已知限制

- 在一份真实数据上，只有约 3% 的思考节点带文本（6,352 个中的 217 个），其余只有时长，所以因果链主要依靠回复文本和思考时长。
- transcript 格式不是稳定的契约：无法识别的记录类型会被计数，可在诊断页或 `GET /api/diagnostics` 查看。
- 等待权限确认的工具会一直保持该状态，直到它的结果到达。
- 复盘时，抽屉里显示的是节点现在的内容（例如工具最终的输出），不是所选时刻的内容。
- 复盘不重现“等待权限确认”的过程：一个节点在结束之前一律显示为执行中。
- Windows 是经过测试的平台。
- 后台派出的子代理：派发节点在子代理真正结束时才结算，耗时是从派出到结束。结束信号有：主线收到的任务通知（同时给出成功或失败）、SubagentStop hook、子代理记录里的 end_turn / 交回调用 / 中断。多个信号以任意先后到达结果都一样：有失败信号就记为失败并取失败的时间，否则取最早的时间。没有自己的结束信号时：同一个子代理之后又被后台派出过，就算在那次派出开始时结束；否则派出之后会话结束过，就记为失败（之后恢复会话也不会让它回来，原来的进程已经没了），都不是则保持“执行中”。同一个子代理被后台派出多次时，每次派出只认自己时间段里的信号。
- 以上信号都没有、会话也没有结束时（例如进程被直接杀掉），派发节点的状态仍是“执行中”。主线不再推进时（会话已结束、空闲、等待输入，或运行中但超过 15 分钟没有动静），主线上仍在执行的步骤显示为“未结束”；后台工作（子代理的步骤和派发节点）多留 5 分钟：只要会话没结束、最近 5 分钟内还有记录，就仍算在进行，因为主线空闲时后台子代理可能还在工作。复盘视角显示的是历史，不受此影响。显示为“未结束”时，画布、瀑布图和详情抽屉都用虚线、无动效的样式，不再声称正在进行。

- Cursor：数据库的格式没有公开文档，是按实际观察到的形状读的；Cursor 升级后可能出现未识别的记录（诊断页的 Cursor 一栏可见），需要跟着更新。
- Cursor：没有“等待权限确认”状态；思考内容只有 Cursor 存下来的那部分文本；不显示 token 用量。
- Cursor：一条记录的内容改回到和之前某一版完全相同时，不会再存一次；重建后该节点停在中间那一版，直到它下一次变化。
- Cursor hooks 的载荷字段和 Windows 上的调用方式取自官方文档，还没有用真实的 Cursor 核对过。
- Cursor：会话很长（上万步）时，第一次导入需要一段时间，在后台进行。
