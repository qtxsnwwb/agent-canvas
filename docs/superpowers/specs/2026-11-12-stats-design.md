# token 补齐与统计面板 设计规格

- 日期：2026-11-12
- 状态：待评审
- 前置：主规格 `2026-11-10-agent-canvas-design.md`。本文只写新增的部分。

## 1. 目标

现在只能一个会话一个会话地看。这一项回答跨会话的问题：时间花在哪、哪类工具调用最慢、哪些命令最常失败、token 用了多少，以及三种工具（Claude Code、Codex、Cursor）在同一个项目上的差别。

分两部分：

1. **token 补齐**：让 Codex 的会话也有 token 用量（现在只有 Claude Code 有）。
2. **统计页**：一个新页面，汇总全部会话的数据，可按时间范围、项目、来源筛选。

### 成功标准

- Codex 会话的节点带上 token 用量，复盘视角的合计不再是 0；升级后自动重建一次。
- 统计页在本机的真实数据量下（约 21 万个节点）首次打开 3 秒内出结果，之后切换筛选 1 秒内。
- 页面上的每个数字都能说清楚是怎么算的（见第 4 节），并且和单个会话里看到的对得上。
- 没有数据的指标如实显示为“—”并说明原因，不显示 0 充数。

### 不做

- Cursor 的 token 用量：Cursor 的数据库里每一步的 token 计数全是 0（本机 19 万条记录无一例外），没有可用的数据。统计页里 Cursor 的 token 显示“—”。
- 把 token 换算成金额（各家价格和套餐不同，以后单独做）。
- 导出、定时报告。

## 2. 本机事实（2026-11-12，只看结构和数量）

| 来源 | token 数据 |
|---|---|
| Claude Code | 已有：节点上的 `usage { inputTokens, outputTokens }`，本机 29,500 个节点带用量 |
| Codex | 原始记录里有，但还没用上：`token_usage_record`（每次模型响应一条，带 `response_id`、`turn_id`、`usage { input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens, total_tokens }`），本机 6,000 条；另有 `event_msg/token_count`（累计值和最近一次的值），6,024 条 |
| Cursor | 没有：每个气泡的 `tokenCount` 全为 0 |

## 3. token 补齐（Codex）

- 用 `token_usage_record`：它是“每次模型响应用了多少”，不是累计值，不需要做差。`event_msg/token_count` 不用（它是累计值，且和前者重复）。
- 归属：一次响应的用量记到这次响应产生的**第一个节点**上（和 Claude Code 现在的做法一致：一条助手消息的用量只记一次，不重复计入它的每个内容块）。靠 `response_id` 对应；对不上的记到同一轮次里时间上最近的前一个节点；整轮都没有节点时丢弃并计数。
- 字段映射：`inputTokens = input_tokens`，`outputTokens = output_tokens`。缓存命中等细分暂不进模型。
- 子代理线程的用量记在子代理线程自己的节点上。
- `NORMALIZER_VERSION` 递增，升级后自动重建（只读我们自己库里已存的原始记录）。
- 这些记录目前被当成“已知但忽略”的类型；改成被消费后，诊断页的未识别记录计数不应因此变化。

## 4. 统计的口径

所有指标都从已推导的节点和会话算出，不读原始记录。

| 指标 | 定义 |
|---|---|
| 会话数 | 在所选范围内有活动的会话数（见 4.1） |
| 轮次数 | 主线程上的轮次数（一条用户提示开始一轮）；子代理内部的轮次不计 |
| 活跃时长 | 所选范围内各轮次的时长之和。轮次时长 = 该轮最后一个节点的结束时间（没有则开始时间）− 该轮提示的时间。仍在进行的轮次算到“现在”，但超过 15 分钟没有活动的不再增长（按最后一次活动时间截止） |
| 工具调用数 | 工具节点和子代理派发节点的数量，含子代理内部的 |
| 失败率 | 状态为失败或已拒绝的工具调用数 ÷ 已结束的工具调用数。仍在执行的不计入分母 |
| 工具耗时 | 各工具调用的耗时之和（并行的调用各算各的，所以它可以大于活跃时长；页面上注明） |
| token | 节点 `usage` 的合计，分输入和输出。Cursor 没有数据，显示“—” |

按工具汇总时，工具名按来源各自的名字显示，不做跨来源的合并（`Bash`、`exec`、`run_terminal_command_v2` 不是同一个东西，合并会误导）；三家对比里用“每轮平均调用数”这类不依赖名字的指标。

### 4.1 时间范围与归属

- 范围：最近 7 天（默认）、最近 30 天、全部。按服务所在电脑的本地时区分日。
- 一个轮次属于它开始的那一天；一个会话在范围内有任何轮次，就算范围内的会话。范围只截取范围内的轮次，不把整个会话都算进来。
- 标记为“源文件已删除”的会话照常统计（数据还在）。

## 5. 接口

`GET /api/stats?range=7d|30d|all&origin=<来源>&projectId=<项目>`，后两个可省略。返回：

- `totals`：会话数、轮次数、活跃时长、工具调用数、失败数、工具耗时、输入 / 输出 token（没有数据时为 `null`）。
- `byDay`：范围内每一天一项（没有活动的日子也在，数值为 0），含轮次数、活跃时长、工具调用数、失败数、token，并按来源拆分。
- `byOrigin`：每个来源一项，含上面的总量，以及每轮的中位时长、每轮平均工具调用数、失败率、每轮平均 token。
- `byProject`：每个项目一项（按活跃时长降序，最多 20 个，其余合成“其他”）。
- `byTool`：每个（来源，工具名）一项：调用数、失败数、总耗时、中位耗时、P95 耗时；按总耗时降序，最多 30 个。
- `slowest`：范围内耗时最长的 10 个工具调用：会话 id、节点 id、来源、工具名、耗时（用于跳转到那个会话）。
- `mostFailing`：失败次数最多的 10 个（来源，工具名），含失败数和失败率；调用数不足 5 次的不上榜。
- `generatedAt`，以及 `coverage`：各来源参与统计的会话数，和“token 无数据”的来源列表。

接口返回的不含任何对话内容（没有提示、参数、输出），只有计数、时长、名字和 id。

### 5.1 计算与性能

- 每个会话算一份**会话小结**（按轮次：开始时间、时长、工具数、失败数、token；按工具：每次调用的耗时和结果），缓存在内存里，键是会话 id 加它最近一次变更的序号；会话变了才重算那一个。
- 请求到来时把各会话的小结按范围和筛选条件汇总。首次请求要为所有会话建小结（本机约 21 万个节点），之后只重算变过的会话。
- 小结的内存有上限（按会话数淘汰最久没用的）；被淘汰的下次用到再算。
- 建小结时分批让出，不长时间占用服务；统计请求之间互不重复计算（同时到达的请求共用同一次计算）。

## 6. 页面

顶栏加“统计”入口（在“通知”“诊断”旁边），页面 `#/stats`。

布局自上而下：

1. **筛选条**（一行）：时间范围（7 天 / 30 天 / 全部）、来源（全部 / Claude Code / Codex / Cursor）、项目（下拉，默认全部）。选择记在浏览器里。
2. **总量**：一排数字卡片——会话、轮次、活跃时长、工具调用、失败率、token（输入 / 输出）。数字卡片不是图表，只放数字和单位。
3. **每天的活跃时长**：按天的柱状图，按来源堆叠。
4. **三家对比**：一张表，每个来源一行，列是会话数、轮次数、每轮中位时长、每轮平均工具调用、失败率、每轮平均 token。没有数据的格子显示“—”。只有一个来源有数据时这一节不显示。
5. **时间花在哪类工具上**：横向条形图，每个（来源，工具名）一条，长度是总耗时，旁边写调用数和中位耗时。
6. **最慢的 10 次调用**和**最常失败的工具**：两张表；最慢的每一行可以点，跳到那个会话并选中那个节点。
7. **按项目**：表，每个项目的会话数、轮次数、活跃时长、失败率、token。

每一节标题下有一行小字说明口径（来自第 4 节）。加载中、加载失败、范围内没有数据三种状态都有明确的显示。

### 6.1 图表的规则

图表用手写的 SVG，不引入图表库。实现前先读数据可视化规范（`dataviz` 技能目录下的 `references/` 各文件），并遵守：

- **先选形式再选颜色**：每天的活跃时长用柱状图（随时间变化的量）；工具耗时用横向条形图（比较大小、名字长）；总量用数字卡片，不画图。
- **一个纵轴**：不做双轴图。时长和次数是两种量，分开两张图或放进表格。
- **颜色只表示来源**：三个来源各用一个固定的颜色，全页一致，和现有的来源标记同色系；筛选后剩下的来源颜色不变。失败、成功等状态不借用这三种颜色。
- **颜色要算过**：用规范自带的校验脚本（`scripts/validate_palette.js`）在本页的浅色背景上校验这三种颜色的可区分度（含色觉障碍），不通过就调整到通过；把最终色值和校验结果写进实现报告。
- **不只靠颜色**：多于一个来源时有图例，并且堆叠的每一段在悬停提示里写明来源名和数值；表格本身就是可读的替代形式。
- **标记**：细柱、数据端 4 px 圆角、相邻填充之间留 2 px 间隙；网格线和坐标轴用很淡的颜色；文字用正文的墨色，不用系列颜色。
- **悬停**：柱和条有悬停提示（日期、来源、数值），命中区域比图形本身大；键盘可聚焦。
- **画完要看**：实现后在浏览器里实际打开，检查标签有没有重叠、溢出。

## 7. 错误处理

- 单个会话的小结计算失败：跳过这个会话，在 `coverage` 里计数，其他照常。
- 没有任何会话、或范围内没有数据：返回全 0 / 空列表，页面显示“这段时间没有活动”。
- 参数不合法（未知的范围、来源）：400。

## 8. 测试

- token 补齐：合成的 Codex 记录覆盖响应到节点的归属、对不上时的回退、子代理线程、不重复计数；重放结果与实时一致。
- 口径：用合成的图逐条验证第 4 节的定义——跨天的轮次归属、进行中的轮次、并行调用的耗时、失败率的分母、子代理内部的调用、范围截取。
- 接口：筛选组合、空数据、不合法参数、返回里不含对话内容。
- 性能：一个默认跳过的基准，20 万个节点规模下首次汇总和增量汇总的耗时。
- 页面：纯函数（格式化、坐标计算、图例、筛选状态）有单元测试；实际观感在浏览器里核对。
- 真实数据：在本机数据上核对总量与各会话页面看到的一致（抽查几个会话）。
