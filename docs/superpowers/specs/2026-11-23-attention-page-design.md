# 待处理页：哪些会话在等你

状态：设计（已确认，未实现）
日期：2026-11-23

## 1. 目的

同时开着好几个编码代理时，用户想一眼看出**哪些会话需要自己出手**：在等批准、出错停了、跑完一轮在等下一句话、卡住了。这个页面只回答这一个问题。它不是“谁在忙”的监控墙：顺利运行的会话不需要用户，不占主列表。

这是用户挑的五个新方向里的第一个（其余是子代理时间线、用量预算、书签批注、两会话对比，各自另行设计）。

### 1.1 目标

- 一个页面列出此刻需要用户的会话，按紧急程度排，每行说明为什么需要用户，点一下进入那个会话、定位到相关的那一步。
- 用户可以把一条“知道了”移出列表；没处理的过一段时间自动移出。会话再次需要用户时重新出现。
- 列表随会话变化实时更新；服务重启、重建数据库后结果不变。

### 1.2 不做的

- 不在这个页面上直接操作代理（批准、回复）。本程序对工具只读。
- 不改通知：通知照旧，这个页面与通知的开关无关。
- 不新增工具状态的判断能力：某个工具本来就认不出的状态（例如豆包分不清跑完和在跑），这里照实说“无法判断”，不去猜。

### 1.3 反目标

- 列表被陈旧的会话塞满，真正要处理的被淹没（所以要有移出和自动移出）。
- 页面和通知对同一件事说法不一致（例如通知说“出错中断”，页面说“跑完了”）。

## 2. 做法的选择

考虑过三种：

| 做法 | 说明 | 结论 |
|---|---|---|
| A. 按会话当前状态现算 | 服务对近期会话，根据它现在的状态、最后一轮怎么结束、相关的那一步，算出需不需要用户；会话一变就重算这一个并推给网页；“知道了”存在服务的数据库里 | **选用** |
| B. 复用通知的判断，每次判断记一条 | 各工具的细节现成；但通知不补发服务重启前、导入历史时的事，重启后列表会是空的；记的是“发生过什么”而不是“现在怎样”，用户在终端里回复后不会自己消失 | 不用 |
| C. 全在网页里算 | 要逐个取会话的步骤，请求多；“知道了”无法在多个窗口之间同步 | 不用 |

A 的代价：通知那边已经按十一种工具写过“这一轮是出错结束还是正常结束”的判断。A 必须**复用**这些判断（抽成共用的函数），不能另写一份；抽取时通知的行为不能有任何变化。

## 3. “需要你”的定义

只看会话的主线（子代理线程不算）。一个会话在某一时刻至多处于下面四种“待处理”状态中的一种，排在前面的优先：

| 种类 | 条件 | 这一段从何时算起（`since`） |
|---|---|---|
| `permission` 等你批准 | 会话状态是 `awaiting_permission` | 进入等待的那一步的时间（状态为 `awaiting_permission` 的节点；找不到时取会话最近活动时间） |
| `error` 出错中断 | 会话状态是 `idle` 或 `awaiting_input`，且最近一个提问之后的这一轮以出错或中断结束。“出错或中断”的认定与通知完全相同（见 4.1） | 出错标记的时间 |
| `stuck` 卡住了 | 会话状态是 `running`，且超过通知设置里的“卡住阈值”（`stuckMinutes`，默认 15 分钟）没有动静 | 最近活动时间 |
| `finished` 跑完了 | 会话状态是 `idle` 或 `awaiting_input`，且不是 `error` | 最近活动时间 |

**没有单独的“等你输入”**（用户决定）：装了钩子的 Claude Code 在一轮结束约一分钟后会由 `idle` 变成 `awaiting_input`。两者都算这一轮的“跑完了”（或“出错中断”），`since` 不变，是同一段，“知道了”不会因此失效。这与通知的处理相同（`engine.ts` 的 `FINISHED`）。

**“卡住了”跟通知设置走**（用户决定）：阈值读通知设置的 `stuckMinutes`，通知关着时也读这个值，两边对同一个会话的说法始终一致。它可能与会话卡片上“长时间无活动”（固定 15 分钟）不同，卡片只显示状态，不叫用户处理，接受这个差别。

不算“需要你”：`ended`（会话已结束）、`sourceDeleted`（源文件已删除）、`running` 且未超时、主线上还没有任何提问的会话（例如 Claude Code 在 `SessionStart` 时就是 `idle`，刚开始的 Qwen 会话也是）。

**“最近活动时间”不用会话的 `lastActivityAt`**（审读意见，我的决定）：它会被任何钩子、子代理线程的记录、一轮结束后才写进文件的记录推后，导致“知道了”反复失效，子代理也会影响主线。上表里凡写“最近活动时间”的，都指**主线最后一个节点的时间**。

**子代理在等批准**（我的决定）：子代理的批准请求也会让会话变成 `awaiting_permission`，算作 `permission`，相关节点是子代理里那个调用，点进去定位到它。

`finished` 不设最短时长：通知里“这一轮至少跑 60 秒才提醒”是为了少打扰，页面不需要；短的一轮跑完了也是在等用户。

### 3.1 无法判断的来源

`grok`、`copilot`、`doubao` 三个来源分不清“跑完了”和“还在跑”（手册“通知”一节的表）。它们的会话**不进主列表**，在页面底部单独计数为“无法判断是否在等你”，可以展开看。这个名单是一个常量，与手册的表一致。

Qwen Code 只有写了一轮结束记录的版本才认得出跑完了；没写的会话一直显示运行中，会按 `stuck` 进入列表。这与通知的行为一致，手册已写明，不另作处理。

### 3.2 一段“待处理”的身份

一段待处理由（会话 id，种类，`since`）确定，称为它的**键**。会话离开这个状态再进入（例如用户回复后它又跑完一轮），`since` 变了，就是新的一段。同一轮里从 `finished` 变成 `error`（迟到的出错标记）也是新的一段。

## 4. 服务端

### 4.1 判断“出错或中断”

现在 `notify/engine.ts` 认定一轮出错或中断的依据是：

- 主线上 `kind === 'system'` 且 `systemSubtype === 'interrupt'` 的节点（Claude Code、Codex 以及读会话文件的各来源的“Turn failed” / “Interrupted” 节点）；
- Cursor：主线的调用节点因对话被中止而变为 `failed`（`isAbortedCall`）；
- 钩子：Claude Code 的 `StopFailure`，Cursor 的 `stop` 且 `status` 为 `error` / `aborted`（`isErrorHook`）。

通知引擎按变更批次增量处理，手里没有会话的主线节点列表，所以能共用的是两样判断（审读意见，我的决定）：**单个节点是不是出错标记**（含 Cursor 的中止调用），和 **`isErrorHook`**（含 Codex 的 `Interrupt` 钩子，上面漏列了）。把这两样抽到通知与本功能都能用的地方，通知改为调用它们；本功能在此之上判断“最近一个提问之后有没有出错标记”。**通知的输出必须与改动前逐字相同**，用现有通知测试和一组新的对照测试证明。

只靠钩子、不在节点上留下痕迹的出错（Claude Code 的 `StopFailure` 就是这样）：**照样认出来**（用户决定）。钩子的原始事件存在 `raw_event` 表里（事件名、收到时间、正文），重启和重建后都在；本功能读最近一个主线提问之后的这些事件，用同一个 `isErrorHook` 判断。这样页面与通知对这种情况的说法一致。

### 4.2 计算与推送

- 候选会话：主线最后一个节点的时间在 30 天以内的会话（主列表再按自动移出时限筛，其余进“已移出的”）。
- 每个候选会话算出它的待处理项（或无），连同“为什么”的一行说明（见 4.3）。
- 会话有变化时（变更流里的 `session_upserted`、主线节点的增删改）只重算这一个会话，通过现有的 WebSocket 推给订阅了它的页面。
- 重算不能读整张图（存储没有“某时刻之后的主线节点”这种查询，10 万节点的会话读整张图很慢）：每个候选会话在内存里维护判定所需的少量状态（最近一个主线提问的时间、此后的出错标记、等待批准的节点、最后一个主线节点），由变更流增量更新；启动时从存储取一次。同一会话短时间内的多次变化合并推送。（审读意见，我的决定；具体做法留给实现。）
- 接入位置不能放在 `if (notifications !== undefined)` 里面：通知服务只在 `start` 时才有，本功能在测试和 `buildServer` 里也要能用。
- 只由时间引起的变化（运行中的会话变成 `stuck`、超过时限被自动移出）在一分钟内反映到页面上。
- 启动导入、重建期间照常计算，不需要像通知那样压住。

### 4.3 每行的说明

| 种类 | 说明取自 |
|---|---|
| `permission` | 等待批准的那一步的工具名和摘要（命令、文件路径） |
| `error` | 出错标记节点的标题或摘要的开头 |
| `finished` | 主线最后一段回复的开头 |
| `stuck` | 最近一步的标题 |

只送节点已有的标题和摘要，截到 200 个字符。这些属于对话内容，网页按页面上的遮蔽开关处理，与会话卡片、画布相同。附带相关节点的 id，供点击时定位。

### 4.4 “知道了”与自动移出

- “知道了”存一个键。当前这一段的键与存的相同，就不在主列表里；键不同（新的一段）就重新出现。
- 自动移出：`since` 早于“现在减时限”的不在主列表里。时限默认 24 小时，可设 1 到 720 小时。
- 两者移出的都可以在“显示已移出的”里看到，并能撤销“知道了”。超时移出的会话即使已不在候选范围，也照样列在这里。
- “显示已移出的”只列 `since` 在 30 天以内的（用户决定）；更早的不再显示，相应的“知道了”记录也删掉。一直停在等批准的会话（例如终端被直接关掉）因此不会无限累积。
- 存在服务的数据库里，与通知设置同样用 `meta` 表的一个键（不改表结构）：时限，以及“知道了”的键。会话已不再是候选的、或键早于 30 天的记录在写入时顺带删掉，使存储有界。
- 不同浏览器、多个窗口看到的相同。

### 4.5 接口

形状由实现决定，需要的能力是：

- 取当前列表：主列表的项（种类、会话的标题、来源、项目、`since`、说明、相关节点 id、键），已移出的项及移出原因，“无法判断”的会话数，正在顺利运行的会话数，时限。
- “知道了”某个键；撤销。
- 读、改时限。
- 改动类的请求与现有的写接口一样要求同源的 JSON 请求（`sameOriginJson`）；数据库整理期间回 503，照通知设置的先例。
- 说明文字的遮蔽沿用 `maskAnomalyList` 的做法；点进节点用已有的路由 `#/s/<id>/n/<node>`。

## 5. 网页

```
待处理（3）                                   [显示已移出的]

● 等你批准  · Claude Code · agent-canvas          2 分钟前
  要执行：npm publish ./release                    [知道了]

● 出错中断  · DeepSeek · 文档工作区               15 分钟前
  一轮以错误结束：请求超时                          [知道了]

● 跑完了    · Codex · fe-app                      1 小时前
  最后的回复：已经改好，测试全部通过……              [知道了]

运行中 4 个 · 无法判断状态的 2 个（豆包、Grok）     [展开]
```

- 顶栏加“待处理”入口，旁边显示主列表的条数（0 时不显示数字）。首页的“N 个正在进行”改为指向这个页面。
- 排序：先按种类（`permission`、`error`、`stuck`、`finished`），同类里 `since` 新的在前。
- 点一行进入会话画布，定位到相关节点；“知道了”按钮不触发跳转。
- “显示已移出的”展开后，每项注明是“知道了”还是“超过 N 小时”，前者可以撤销。
- 时限在页面上改。
- 实时更新，不用刷新。
- 列表为空时说一句“此刻没有需要你处理的会话”，并给出运行中的数量。
- 名称、颜色、图标沿用现有的状态样式；新颜色按现有方式校验。

## 6. 测试

只用临时目录和自造数据，不读真实的工具目录；不弹真实通知。

| 要证明的事 | 做法 |
|---|---|
| 四种状态的判定和优先次序 | 每种一例；同时满足多种时取优先的；`idle` 变 `awaiting_input` 仍是同一段 |
| 出错的判定与通知一致 | 对十一个来源各用通知测试里已有的“出错”“正常结束”场景，本功能判定的种类与通知发出的种类相同；通知测试全部不变地通过 |
| 抽取后通知不变 | 对一批随机变更流，抽取前后的通知输出逐字相同 |
| 无法判断的来源 | `grok`、`copilot`、`doubao` 只计数，不进主列表 |
| 段与键 | 回复后再次跑完是新的一段；`finished` 变 `error` 是新的一段；“知道了”只移出当前这一段 |
| 自动移出 | 时限边界两侧；改时限立即生效；超时移出的出现在“已移出的”里；30 天以上的不再出现 |
| 只靠钩子的出错 | `StopFailure` 之后，页面显示“出错中断”，重启、重建后不变 |
| 卡住阈值 | 改通知设置的 `stuckMinutes` 后，页面随之变化 |
| 重启与重建 | 同一批数据，重启后、重建后列表与之前相同；“知道了”保留 |
| 实时 | 会话变化后页面收到更新；只由时间引起的变化在一分钟内出现 |
| 存储有界 | 大量“知道了”之后旧记录被清掉 |
| 遮蔽 | 说明文字随遮蔽开关遮蔽 |
| 子代理 | 子代理线程的活动不影响主线的判定 |

Linux 和 Windows 的 CI 都运行。

## 8. 留给实现的

- “只由时间引起的变化”用服务端定时重算还是网页按时钟推导。
- 抽出的共用判断放在哪个文件。
