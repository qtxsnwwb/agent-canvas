# 异常检测 设计规格

- 日期：2026-11-13
- 状态：待评审
- 前置：主规格 `2026-11-10-agent-canvas-design.md`，以及通知（`2026-11-12-notifications-design.md`）、统计（`2026-11-12-stats-design.md`）、按文件看（`2026-11-12-files-design.md`）、检索（`2026-11-13-search-and-storage-design.md`）。本文只写新增和改动的部分。

## 1. 目标

统计页回答“总体上时间花在哪、什么最常失败”，通知回答“现在要不要我出手”。还缺一块：**单个会话内部值得回头看一眼的模式**——代理卡在循环里、一连串失败、同一个文件改个没完、某一轮消耗离谱。这些既不是单次失败，也不是单次慢调用，现有页面上看不出来。

### 成功标准

- 打开首页就能看到哪些会话出过异常；打开会话能看到是哪一轮、哪一类，点一下定位到相关步骤。
- 正在运行的会话出现“原地打转”或“失败扎堆”时，可以收到一条桌面通知（默认关）。
- 本机数据上，被标出的轮次是少数（目标：约 1% 的量级），不是满屏标记。实际数字在实现后测量并写进本文。
- 重建后的结果与实时计算一致。

### 不做

- 自定义阈值、自定义规则。
- 自动打断或干预会话：只提醒。
- 对某条异常“忽略 / 标记已读”。
- 用模型判断异常：全部是确定的规则。

## 2. 本机事实（2026-11-13，只看数量）

37 个会话，5,823 个轮次（主线和子代理内部各自成轮）。以“工具名 + 摘要前 200 字”粗略代表“同一个调用”：

| 候选规则 | 标出的轮次 |
|---|---|
| 同一个调用在一轮里出现 ≥5 次 | 785 |
| 同一个调用连续 ≥5 次 | 274 |
| 同一个调用失败 ≥3 次 | 58 |
| 连续失败 ≥5 次 | 19 |
| 同一文件一轮里改 ≥8 / ≥10 / ≥15 次 | 191 / 149 / 40 |
| 主线一轮的墙上时间 ≥ 项目中位数 5 倍且 ≥10 分钟 | 271 |
| 主线一轮的工作时间 ≥ 同项目同来源 95 分位的 2 倍且 ≥10 分钟 | 48 |
| 主线一轮的 token ≥ 同项目同来源 95 分位的 2 倍且 ≥20 万 | 11 |

结论：“出现次数”和“墙上时间”不能用（正常工作也会这样；墙上时间含等用户的时间）；摘要当作调用的身份太粗，要用完整输入。

## 3. 规则

阈值是共享包里的常量。

### 3.1 轮次

一个**检测轮次**是同一条线（主线，或某个子代理）里，从一条提示到下一条提示之前的节点，按时间再按 id 排序。主线的轮次与画布的分组一致（复用 `groupTurns` 的规则）；子代理内部按同样的规则各自分轮，没有提示的子代理整条线算一轮。派发节点属于派出它的那条线。

### 3.2 输入指纹

工具节点和派发节点新增 `inputKey?: string`：工具名与**完整输入**的规范化形式（对象键排序后的 JSON）的哈希，取 16 个十六进制字符。整段输入都参与哈希（不截断）；字符串输入与对象输入带不同的类型标记，不会互相撞上。三个归一化器在写入（或改写）节点输入的地方计算，指纹跟着最终的输入走。它只是哈希，不含内容；输入缺失时不设；Cursor 的气泡后来的记录丢了参数时保留上一次的指纹（与“节点保留最后一次可识别的形状”一致）。两个节点 `toolName` 相同且 `inputKey` 相同，才算“同一个调用”。归一化版本加一。

### 3.3 四类异常

| 类型（`kind`） | 判定 | 何时能判 |
|---|---|---|
| 原地打转 `loop` | 一轮里，同一个调用失败 ≥ `LOOP_FAILED_MIN`（3）次；或同一个调用连续执行 ≥ `LOOP_REPEAT_MIN`（5）次（中间没有别的工具调用） | 实时 |
| 失败扎堆 `failures` | 一轮里连续 ≥ `FAILURE_STREAK_MIN`（5）次工具调用以失败结束（按结束顺序；被拒绝的不算失败，也不打断连续） | 实时 |
| 反复改同一个文件 `churn` | 一轮里同一个文件的 `edit` / `write` ≥ `CHURN_MIN`（15）次（失败、被拒绝的不算；路径按 `pathKey` 判同） | 实时 |
| 消耗异常高 `cost` | 主线的一轮结束后，它的工作时间或 token 超过基线（见 3.4） | 一轮结束后 |

- 一轮里同一类只报一条（`cost` 的时间和 token 各算一种，可以各报一条）。同一轮同时满足 `loop` 的两个条件时报一条，取先满足的那个为依据。
- 每条异常记录：类型、会话、所在的线（`agentId`）、轮次的键、依据（哪种条件）、次数或数值、涉及的节点 id（第一个和最后一个，定位用最后一个）、文件路径（`churn`）、工具名（`loop`，工具名不是对话内容）、发生时间（满足条件的那个节点的时间，ISO 8601）。**不含任何对话或输入内容。**
- 正在执行的节点不算失败；节点之后改了状态，结果跟着变（检测是当前节点集合的纯函数）。
- 时间戳无法解析的节点“无法判断”：不参与检测——不算调用、不算失败、不算改文件，也不打断“连续”；它不提供发生时间，也不计入轮次消耗（不算时间和 token，不决定轮次的开始和结束）。结束时间无法解析时按“结束时间未知”处理：连续失败按开始时间排序；判断 `loop` 的两个条件谁先满足时，结束时间未知的失败排在所有已知结束时间的失败之后（状态晚到时依据不会因此往回跳）。
- `churn` 里一个节点对同一个文件只算一次（既 edit 又 write 也是一次）。

### 3.4 消耗基线

- 一轮的**工作时间** = 这一轮里工具节点、派发节点、思考节点的耗时之和（不含等用户的时间；并行的调用各自计入）。一轮的 **token** = 这一轮计入用量的节点的“新输入 + 输出”（与统计页的口径一致，不含缓存读取）。
- 基线按（项目，来源）分组，取该组所有已结束的主线轮次的 95 分位。组内轮次少于 `COST_MIN_TURNS`（20）时不判。
- 判定：数值 ≥ `COST_FACTOR`（2）× 95 分位，并且 ≥ 保底线（工作时间 10 分钟，token 20 万）。
- Cursor 没有 token 数据，只判工作时间。
- “已结束的轮次”：它后面已经有下一条提示，或会话不在运行中。
- 基线随数据变化：新的轮次会让旧的判定略有变动，这是预期的；同一份数据算出来的结果是确定的。

## 4. 服务端

- 纯函数放共享包 `packages/shared/src/anomalies.ts`：`detectAnomalies(nodes)`（前三类）和 `turnCosts(nodes)`（每个主线轮次的工作时间和 token），以及在给定基线下判 `cost` 的函数。
- 服务端 `packages/server/src/anomalies/`：沿用统计的 `SessionSummaryCache`——每个会话缓存“它的前三类异常 + 它的轮次消耗”，会话有变更才重算自己；`cost` 在查询时用所有会话的轮次消耗现算基线再判。启动后后台预热。
- 接口（都只返回类型、数量、时间、id、路径）：
  - `GET /api/sessions/:id/anomalies` → 这个会话的异常列表。
  - `GET /api/anomalies?range=&origin=&projectId=&kind=` → 跨会话列表（`range` 同统计页：`7d` / `30d` / `all`，默认 `30d`），按时间倒序，最多 200 条，超出时标明；附带每类的总数。
  - `GET /api/anomalies/counts` → 每个会话的异常条数（首页标记用）。
- 参数不合法：400。预热未完成时接口照常应答，并标明“仍在计算”。

## 5. 通知

- `NotificationKind` 新增 `loop` 和 `failures`，“通知”页各一个开关，默认关（总开关仍是前提）。
- 只针对正在运行的会话，且异常发生在最近 2 分钟内（启动时导入历史数据不弹）。同一会话、同一轮、同一类只弹一次；服务重启后不重弹已有的。
- 文案只含类型、会话标题和次数，例如“原地打转：同一个命令已经失败 3 次”。点击打开该会话并定位到相关节点。
- `churn` 和 `cost` 不弹通知。

## 6. 页面

- **首页**：会话卡片上有异常时显示一个标记和条数，悬停说明各类各几条。
- **会话页**：
  - 概览里出异常的轮次卡片上有标记（子代理里的异常标在派出它的那一轮和对应的子代理卡片上）。
  - 工具栏新增“异常”按钮（带条数），打开面板列出每一条：类型、哪一轮、依据和次数、时间；`churn` 显示文件路径。点一条：选中并定位到相关节点（复用 `#/s/<id>/n/<nodeId>` 的定位）。
  - 没有异常时按钮不带数字，面板写“这个会话没有发现异常”。
- **新页面 `#/anomalies`**（顶部导航“异常”）：跨会话列表，筛选时间范围、来源、项目、类型；每行：来源标记、会话标题、类型、依据和次数、时间，点击跳到会话里的那一步。顶部给出每类的条数。页面上注明这些是启发式规则，可能误报。
- 四类的名称、说明用同一份文案（共享常量），页面和通知一致。
- 加载中、空、出错、“仍在计算”四种状态。

## 7. 错误处理

- 某个会话算异常时出错：这个会话记为失败并计数，其他会话不受影响；接口返回里给出失败的会话数。
- 节点缺字段（没有 `inputKey` 的旧节点、没有耗时、时间戳无法解析）：按“无法判断”处理，不报异常，不崩。
- 通知发送失败：同现有通知，记入通知状态，不重试。

## 8. 测试

- 规则：每一类的刚好达到和差一次；`loop` 的两个条件；中间夹着别的调用时“连续”被打断；被拒绝的调用不算失败也不打断；正在执行的节点；同一轮只报一条；子代理内部；没有提示的子代理；节点乱序输入结果相同；输入指纹对键顺序不敏感、对值敏感。
- 消耗：分位数和保底线的边界；不足 20 轮不判；未结束的轮次不判；Cursor 只判时间；按（项目，来源）分组。
- 三个归一化器的 `inputKey`：同一输入同一指纹；重建与实时一致。
- 服务：会话变更只重算自己；预热中的应答；筛选和 200 条上限；参数校验。
- 通知：只对运行中、刚发生的异常弹；同一轮同一类一次；重启不重弹；开关关闭时不弹。
- 页面的纯逻辑：标记数量、面板行的模型、筛选状态。
- 真实数据：升级前备份；升级后核对三种来源的会话数、节点数与升级前一致；量出每类标出的轮次数和会话数，写进本文；抽查若干条跳转是否落在对的节点上（只看 id 和类型，不看内容）。
