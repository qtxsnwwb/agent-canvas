# 全文检索与数据库瘦身 设计规格

- 日期：2026-11-13
- 状态：已评审通过并实现；真实数据的核对待做（文中标“待真实数据核对”的数字由升级后实测填入）
- 前置：主规格 `2026-11-10-agent-canvas-design.md`。本文只写新增和改动的部分。

## 1. 目标

两件事，放在一起做是因为它们互相牵制：全文检索要建索引、会让数据库变大，瘦身要让它变小。

1. **全文检索**：现在的检索只找会话标题、分支、目录和每条提示的前 200 个字，找不到回复、命令和工具输出。改成能搜到会话里的内容，并直接跳到命中的那一步。
2. **数据库瘦身**：本机数据库已经 2.5 GB（Cursor 接入后翻了一倍多）。在不丢任何数据的前提下把它压小。

### 成功标准

- 搜一个出现在回复、命令或工具输出里的词（中文、英文、路径、报错信息都行），能找到它所在的会话和具体的那一步，点击跳到那一步。
- 本机数据量下，一次检索在 300 毫秒内返回。
- 升级后数据库文件明显变小：目标是**连同新增的检索索引在内，不超过升级前的 70%**（本机约 1.75 GB 以内）。
- 不丢数据：升级后的重建结果和升级前一致；需要时仍能从原始记录完整重建。
- 升级过程可中断：中途被杀掉，下次启动能接着做，不会留下损坏的库。

### 不做

- 按时间自动删除旧会话（需要时以后单独做，默认永不删除）。
- 正则、通配符、布尔语法：就是“包含这段文字”。
- 语义检索、近义词。
- 检索文件内容本身（只检索会话里记录下来的文字）。

## 2. 本机事实（2026-11-13，只看大小和数量）

数据库 2,522 MB，SQLite 3.53，内置 FTS5（含 trigram 分词器）。空间分布：

| 表 | 大小 | 内容 |
|---|---|---|
| `raw_event` | 1,339 MB（53%） | 原始记录的原文，用于重建。Claude Code 507 MB、Cursor 294 MB、Codex 204 MB、hook 45 MB |
| `node_detail` | 433 MB | 节点详情：工具的输入、输出，回复全文。抽样里输出约占七成 |
| `node` | 228 MB | 节点 |
| `edge`（含索引） | 240 MB | 边 |
| `change_log`（含索引） | 149 MB | 变更流水，给网页断线重连用，现保留最近 20 万条 |
| 其他索引 | 约 130 MB | |

- `raw_event.body` 只在重放（重建、会话重新载入内存）时读，没有任何查询对它做条件过滤。
- FTS5 的 trigram 分词器可以做任意语言的子串匹配，包括中文；但查询至少要 3 个字符，2 个字符（比如两个汉字）匹配不到。

## 3. 全文检索

### 3.1 检索什么

每个节点一条索引文本，由这些部分拼成：

| 节点 | 进索引的文字 |
|---|---|
| 提示 | 全文 |
| 回复 | 全文 |
| 思考 | 全文（有的话） |
| 工具、子代理派发 | 工具名、输入（命令、参数），输出的前 8 KB |
| 系统节点 | 全文（详情里有的话，如报错信息、中断说明、通知），否则摘要（审阅后决定：全文是摘要的超集） |

- 子代理内部的节点一样进索引。
- 输出只取前 8 KB：工具输出占了详情的大部分，全量索引会让索引比原文还大；要找的报错、路径通常在开头。单条索引文本总长上限 64 KB。
- 会话标题、分支、工作目录、会话 id 仍按现在的方式检索（它们在会话表里，量很小）。

### 3.2 怎么建索引

- 用 FTS5 的 trigram 分词器，建成只存索引、不存原文的形式（原文在节点详情里已有一份）。
- 索引跟着节点走：日常的节点新增、更新、删除在**同一个事务**里更新索引。全量重建例外：重建期间不写索引，先把索引标为不完整，重建结束后由后台任务一次建好（见下面的“结论”）。
- 索引的精细程度（是否保留位置信息）由实现时在真实规模上测量后决定：在满足 300 毫秒目标的前提下选体积最小的。测量结果写进本文。

**测量结果与选择（2026-11-13，合成数据，`packages/server/test/search.bench.test.ts`）**：215,000 个节点、2,150 个会话，索引文本共 174 MB（平均每节点 850 字节；提示、回复、思考、工具输入输出，15% 中文，8% 的工具输出在 2–20 KB），直接写入存储（每个会话一次 `applyChanges`，与重建相同）。Windows 11，单次运行。

| | `detail=full` | `detail=column` | `detail=none` |
|---|---|---|---|
| 索引体积 | 441 MB | 256 MB | **93 MB** |
| 写入时维护索引的额外开销 | +197 µs/节点 | +150 µs/节点 | +114 µs/节点 |
| 后台补建（全部节点） | 48 s | 41 s | 31 s（每批 100 个节点，最长一批 47 ms） |
| 罕见词 / 常见词（6,300 个候选）/ 很常见（4.7 万个候选） | 14 / 22 / 54 ms | 13 / 21 / 42 ms | 7 / 21 / 45 ms |
| 中文 4 字 / 路径 / 2 个字 | 16 / 19 / 19 ms | 15 / 21 / 17 ms | 11 / 21 / 16 ms |

（三列的查询时间来自同一轮测量；`none` 一列为调整语料后的复测，数字相同量级。）`none` 下另测：约 100 个字符的长查询，存在 50 ms、不存在（241 个候选全被核对排除）106 ms；同一节点连续更新 2,000 次每次 0.5 ms，索引不增长（FTS5 自动合并即可，不需要另做 optimize）；启动时的一致性检查 21–158 ms。

**选择 `detail=none`**：体积最小，所有查询都远低于 300 毫秒。`none` / `column` 不支持多字符短语查询，查询改为把检索词的每个三字组合用 AND 连起来（只是候选），每个候选都用节点详情里的原文逐条核对，片段也从原文截取。写入开销：不含索引时直接写存储约 70 µs/节点，含索引约 185 µs/节点；按全量重建 21.5 万节点计约多 25 秒。

**端到端开销与全量重建的处理（审阅第 1 轮，2026-11-13，`storage.bench.test.ts` 的 “search index cost end to end”）**：35 万条原始记录（1,056 MB JSONL，233,412 个节点；工具输入 0.5–3 KB、输出 1–6 KB、回复 1–4 KB，比本机实际的单条文字长），走真实管线：首次全量读入（ingest）和全量重建（rebuild），关索引（`off`）与开索引（`none`）交替各跑两轮。机器同时在跑别的程序，单次时间波动很大（同一配置两轮可差一倍多），比例只看同一轮内的前后两次。

| | 关索引 ingest / rebuild | 开索引 ingest / rebuild | 比例（两轮均值） |
|---|---|---|---|
| A：重建时逐节点维护索引（FTS5 automerge/usermerge = 16） | 138.5 / 50.4 s；208.4 / 128.2 s | 248.1 / 131.7 s；572.9 / 338.0 s | ingest 2.37，rebuild 2.63（较干净的第 1 轮：1.79 / 2.61） |
| B：全量重建不写索引，重建后后台一次补建 | 353.8 / 134.9 s；361.1 / 171.9 s | 576.7 / 133.6 s；483.7 / 82.9 s | ingest 1.48，rebuild 0.71（即与关索引相当） |

B 的后台补建：236 s 和 260 s（2,335 批，每批 100 个节点），期间检索返回“索引正在重建”。另测：FTS5 合并参数 automerge/usermerge 从默认 4 调到 16，单纯写索引约省 15%（107 → 87–93 µs/条），体积与查询时间不变，已采用；删除不存在的 rowid 几乎不花时间。

**结论**：
- **采用 B**：全量重建时先把索引标为不完整、重建过程中不写索引，重建结束后由后台任务一次建好（分批、让出事件循环、遇到 VACUUM 暂停）。重建的耗时因此与没有索引时相同，满足“不慢于 1.3 倍”。重建中途或补建中途进程退出：索引仍标为不完整，下次启动接着补建；补建期间到来的新写入照常维护索引，补建从头覆盖全部节点，每个节点只留一行。
- **首次读入（ingest）不满足 1.3 倍**：边读边写索引，测得 1.5–1.8 倍。增量部分就是三字组合分词本身（每个字符一个词元），去掉无变化的重写、调大合并参数后已无明显浪费。首次读入只在第一次安装或换库时发生，之后的日常写入是零星的。若要达标，只能把首次读入也改为“先不写索引、读完后后台补建”，留作以后的选项。

**几点说明（审阅后保留的做法）**：
- 启动时的一致性检查只比较“索引行数 ≤ 节点数”加一个完整标记：能发现孤立的索引行，发现不了“节点写了但没进索引”；后者只可能来自不维护索引的外部写入。凡改动索引文本的规则（`indexTextOf`）都要提高 `SEARCH_INDEX_VERSION`，让索引整体重建。
- 返回里的 `truncated` 是近似的：还有未核对的候选就记为被截断，其中可能有核对后并不命中的。
- 两个字的检索按会话逐行读节点类型，每读一行检查一次时间预算（250 毫秒），没有为它另建部分索引（那会给每次节点写入加开销）。

### 3.3 怎么查

- 内容命中走单独的接口 `GET /api/search/content?q=&origin=&projectId=`（没有 `limit`，上限见下面的截断规则）：每个命中给出会话、节点 id、节点类型、工具名、时间，以及命中处前后各约 40 个字符的片段。原有的 `GET /api/search`（会话标题等）不变。
- 查询规则：
  - 去掉首尾空白，最多取前 200 个字符；至少 2 个字符才检索（和现在一致）。
  - 3 个字符及以上：走全文索引。
  - 恰好 2 个字符（常见于两个汉字的词）：全文索引帮不上忙，改为只在提示和回复里按“包含”逐条查，并且只查最近活跃的会话（默认最近 30 天），页面上注明“两个字的词只在最近的提示和回复里找”。
  - 按字面匹配，不区分 ASCII 大小写。输入里的引号、星号、括号等一律当普通字符，不当语法。
- 排序：先按会话的最近活动时间，同一会话内按节点时间倒序。每个会话最多返回 5 处内容命中，整体最多 50 个会话；被截断时返回里说明。
- 片段从节点详情里取（索引不存原文），截断处用省略号；片段里只有命中附近的文字。

### 3.4 页面

- 首页的检索框不变，结果分两组：**会话**（标题等命中，现有的）和**内容**（新增）。
- 内容命中的每一行：来源标记、会话标题、节点类型和工具名、时间、带高亮的片段。点击跳到那个会话并选中、定位到那一步。
- 为了“跳到那一步”，会话地址支持 `#/s/<会话 id>/n/<节点 id>`：打开时选中并定位那个节点（复用“按文件看”里已经做好的定位逻辑）。统计页“最慢的 10 次调用”也改用这个地址，补上之前“只能跳到会话”的缺口。
- 加载中、没有结果、查询太短三种状态。

## 4. 数据库瘦身

三项都不丢数据。

### 4.1 压缩原始记录

- 原始记录压缩存放（Node 自带的 zlib，不引入依赖）。它只在重放时读，读的时候解压。
- 存放格式（存储格式 1）：数据列改名为 `raw_event.data`（原 `body`），另有标记列 `enc`：0 = 原文（文本），1 = UTF-8 原文的 zlib 流（BLOB；2 字节头 + deflate 级别 1 + Adler-32 校验，比裸 deflate 每行多 6 字节）。校验不过、标记未知、解压超过 16 MiB 都按“这一行损坏”处理。小于 200 字节、大于 16 MiB 或压缩后不变小的记录直接存原文。新旧两种行可以并存。
- 去重靠的是原文的哈希（`line_hash`），不受压缩影响。
- 压缩率（逐行压缩，没有共享字典）：本机实测 Claude Code 0.41、Cursor 0.48、Codex 0.48、hook 0.44、节点详情 0.45；合成数据 0.46。原先估计的 15%–25% 是整文件压缩的比例，逐行压缩达不到。
- 速度（合成数据，20 万条，单次运行、机器有别的负载，波动大）：首次读入约 1.35 倍；全量重建 1.44–2.05 倍（两次运行）。本机实测：待真实数据核对。
- 存储格式记在 `meta.storage_format`。更新的版本写过的库（格式号更高）本版本拒绝打开，不改任何内容；旧版本打开升级后的库会因为找不到 `body` 列而在启动时报错退出，不会误读压缩行。降级的办法只有一个：恢复升级前备份的 `data.db`。

### 4.2 压缩节点详情

- 节点详情同样压缩存放（列名改为 `node_detail.data`，同一套 `enc` 标记）。点开节点、取检索片段时按主键取单行；后台建索引时按节点 rowid 的范围连同节点一起分批读。读不出的详情返回空详情并标记 `unreadable`，计入诊断（`storage.unreadableDetails`）；更新时遇到读不出的详情不覆盖它，而是把会话标为待重新推导。

### 4.3 收紧变更流水

- 变更流水只用于网页断线重连后的追赶；超出保留范围时网页本来就会整页重新加载。保留条数从 20 万降到 5 万。

### 4.3a 精简边表

- 边表改成每条边只存一次：`WITHOUT ROWID`，主键 `(session_id, from_id, to_id, tag)`，类型是小整数，不再存 JSON 和重复的 id（边的 id 由两端拼出）。合成数据（92 字符的节点 id）每条边从 920 字节降到 237 字节。
- 边是推导数据：升级时旧边表直接换掉，推导版本号升到 30，首次启动时全量重建一次（启动前完成，期间页面打不开）。

### 4.4 一次性迁移与回收空间

- 升级后首次启动时（在自动重建之后、启动工作结束后）在后台执行一次迁移：分批把已有的行改写成压缩形式（每批最多 2,000 行或 1 MB 文字、一个事务，批与批之间让出事件循环并等检查点追上，导入期间暂停），在 `meta` 里记进度；中途中断，下次从记录的位置继续。每批之间等检查点，WAL 不会随改写的数据量增长（上限约为 WAL 的大小限制 64 MB 加 16 MB 余量再加一批；缩小比例的测试里为 2–3 MB，不等检查点时是 43–47 MB）。
- 迁移完成后执行一次 `VACUUM` 回收空间。`VACUUM` 先在 SQLite 的临时目录里写一份库的副本，再通过 WAL 把内容写回数据库，所以需要两处空间：临时目录所在的卷和数据库所在的卷各要 1.2 ×（库文件 + WAL）的可用空间；两者在同一个卷上（Windows 上通常都在 C 盘）时这个卷要 2.4 倍。不够就跳过，在诊断数据里给出原因（数据已经压缩，只是文件暂时没变小），之后再启动时或用 `agent-canvas compact` 重试。
- `VACUUM` 在单独的子进程里执行，最长 120 秒（超时就结束子进程，SQLite 自动回滚）；之后的截断检查点最多试 10 次。只有文件确实变小（或本来就没有空闲页）才算完成。执行失败（出错、超时、文件没变小）24 小时内不再自动重试；检查点被别的读者挡住（busy）不受这个限制，下次启动再试。
- 迁移和 `VACUUM` 期间服务照常启动、页面可用；进度、`VACUUM` 状态和原因在 `/api/diagnostics` 的 `storage` 里（诊断页的展示由网页部分完成）。`VACUUM` 期间（本机规模约十几秒，最长 120 秒加检查点）写入暂停：采集到的文件和轮询数据排队等待；hook 先写进数据目录里的 `held-hooks.jsonl`，结束后（或进程中途退出后的下次启动时）写入数据库并删掉这个文件；通知设置的修改返回 503“数据库正在整理，稍后再试”。此时按 Ctrl+C 关闭服务会等 `VACUUM` 结束。
- 新增命令 `agent-canvas compact [--force]`：服务没在运行时手动执行“迁移未完成的部分 + `VACUUM`”，打印前后的文件大小；`VACUUM` 已做过且之后没有新迁移的内容时不再执行；`VACUUM` 失败时退出码为 1；`--force` 不查空间、不管 24 小时的限制强制执行。

## 5. 错误处理

- 某一行解压失败（数据损坏、校验不过、标记未知）：这一行跳过并记入诊断（原始记录记在导入失败里，按文件一条；节点详情计入 `storage.unreadableDetails`），不让整个重放失败；读不出的行从不被覆盖。
- 数据库是更新的版本写的（存储格式号更高）：拒绝启动并说明，不改动数据库。
- 索引和节点不一致（比如上一次异常退出）：启动时做一次轻量检查（两边的行数），不一致就在后台重建索引，期间检索返回里说明“索引正在重建，结果可能不全”。
- 检索的查询参数不合法：400。
- 磁盘空间不足：迁移照常（原地改写；额外占用只有有界的 WAL，约 80 MB 加一批，以及改写后留下、等 `VACUUM` 回收的空闲页，文件在 `VACUUM` 之前不会变小），只跳过 `VACUUM`。

## 6. 测试

- 检索：中文、英文、路径、带引号和特殊字符的查询；2 字符与 3 字符的分界；子代理节点；输出只索引前 8 KB；节点更新和删除后索引跟着变；重建后结果一致；每会话 5 处、整体 50 个会话的截断；片段的截取和高亮位置。
- 压缩：新旧行并存时读写正确；短记录不压缩；损坏的行；去重不受影响；重放结果与压缩前逐字节一致。
- 迁移：中断后续跑；重复执行是空操作；空间不足时跳过 `VACUUM`；迁移期间的读写。
- 性能：默认跳过的基准——本机规模下的检索耗时、索引体积、重建耗时。
- 真实数据：升级前先备份；升级后核对三种来源的会话数、节点数与升级前一致，测量文件大小，抽查几个检索词。
