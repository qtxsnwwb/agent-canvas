# 通知 设计规格

- 日期：2026-11-12
- 状态：待评审
- 前置：主规格 `2026-11-10-agent-canvas-design.md`。本文只写新增的部分。

## 1. 目标

不用盯着页面，也能知道智能体什么时候需要你：会话在等你确认权限、一轮跑完了、出错中断了、卡住很久没动静时，在电脑上弹一条系统通知。

已确认的范围（2026-11-12）：

- 渠道：**只做系统桌面通知**（由本机服务发出，不需要开着网页，不联网）。
- 时机：**等待权限确认、一轮跑完、出错中断、卡住很久**，四种都做。

### 成功标准

- 四种情况各自在发生后几秒内弹出一条系统通知，标题说明是哪种情况，正文是项目名和会话标题；点击通知在浏览器里打开对应的会话。
- 不该弹的时候不弹：启动时导入历史、升级重建、读入别人的旧会话，都不产生通知；同一件事只弹一次。
- 可以在页面上整体开关、按种类开关、调阈值，并发一条测试通知；设置保存在本机，重启后还在。
- 通知发不出去（系统不支持、命令不存在）时，服务照常工作，诊断页能看到原因。
- 三种来源（Claude Code、Codex、Cursor）都适用；某个来源给不出某种信号时，如实说明。

### 不做

- 飞书、Webhook、浏览器通知（以后要加时，在 5.2 的投递接口后面加实现即可）。
- 单个工具调用失败的通知（太频繁）。
- 从通知里直接批准或拒绝权限。

## 2. 默认值

通知**默认关闭**，在页面的“通知”设置里打开。原因：别人通过 npm 安装后，不应该在没同意的情况下开始弹通知。

| 设置 | 默认 | 说明 |
|---|---|---|
| 总开关 | 关 | |
| 等待权限确认 | 开 | |
| 一轮跑完 | 开 | 只提醒运行了至少 `最短时长` 的轮次 |
| 最短时长 | 60 秒 | 0 表示每一轮都提醒 |
| 出错中断 | 开 | |
| 卡住很久 | 开 | |
| 卡住阈值 | 15 分钟 | 和页面上“长时间无活动”的阈值一致，可调（最小 1 分钟） |

## 3. 四种时机的判定

通知引擎订阅现有的变更流（`pipeline.onChanges`），只看会话状态和新出现的节点，不读原始记录。

| 种类 | 判定 |
|---|---|
| 等待权限确认 | 会话状态变为 `awaiting_permission`。离开该状态后再次进入，算新的一次 |
| 一轮跑完 | 会话状态从 `running`（或 `awaiting_permission`）变为 `idle` / `awaiting_input`，且这一段运行持续了至少“最短时长”。运行时长 = 变为空闲的时刻 − 引擎看到它开始运行的时刻（引擎启动时已经在运行的会话，从它的最近一条提示节点的时间算起） |
| 出错中断 | 一轮以错误或中断结束：出现各归一化器用来表示“轮次失败 / 被中断 / 接口报错”的系统节点，或 Claude Code 的 `StopFailure` hook。具体取哪些标记，实现时按三个归一化器现有的输出逐一列出并写进本文 |
| 卡住很久 | 会话状态是 `running`，且最近活动时间距现在超过“卡住阈值”。每次卡住只提醒一次；之后有了新活动再卡住，算新的一次 |

同一轮既出错又变为空闲时，只发“出错中断”，不再发“一轮跑完”。

“出错中断”实际使用的标记（实现时按三个归一化器的输出确定，只看主线，子代理里的不算）：

| 来源 | 标记 |
|---|---|
| Claude Code | `system` 节点，`systemSubtype = 'interrupt'`（用户中断：`[Request interrupted by user…]` 记录）；`StopFailure` hook（它不产生节点，服务在入库前把它交给引擎，会话随后变为空闲时发） |
| Codex | `system` 节点，`systemSubtype = 'interrupt'`：标题 “Turn failed”（`task_complete` 带 `error`）或 “Interrupted”（`turn_aborted`） |
| Cursor | 工具节点变为 `failed` 且其说明是“已中止：对话停止时工具仍在运行。”（会话被中止时仍在运行的调用；说明不在变更流里，引擎按节点 id 查一次） |

限制：Claude Code 转录里的接口报错记录（assistant 消息）在归一化后没有可区分的标记，只能靠 `StopFailure` hook（需要装 hooks）；Cursor 中止时如果没有正在运行的调用，看不出是中止，按“一轮跑完”处理。

### 3.1 不该弹的情况

- **历史数据**：服务启动后的首次导入、自动重建、轮询来源的第一轮期间，一律不发。
- **旧事件**：只有“新近发生”的才发——触发它的那次状态变化或节点，时间距现在不超过 2 分钟。读入一个很久以前的会话（比如新发现的历史文件）不会弹。
- **已删除的源**：标记为“源文件已删除”的会话不发。
- **子代理**：只看会话整体的状态，子代理内部的开始和结束不单独提醒。
- **重复**：每个会话每种通知有“一次”的概念（见上表），同一次不重复发；另外同一个会话同一种通知 30 秒内最多一条，防止状态抖动。

### 3.2 各来源能给出什么

| | Claude Code | Codex | Cursor |
|---|---|---|---|
| 等待权限确认 | 需要装 hooks | 需要装 hooks 并确认信任 | 没有这个状态 |
| 一轮跑完 | ✅ | ✅ | ✅（不装 hooks 时延迟几秒） |
| 出错中断 | ✅ | ✅ | ✅（会话被中止） |
| 卡住很久 | ✅ | ✅ | ✅ |

## 4. 通知的内容

- 标题：`<种类> · <项目名>`，例如“等你确认权限 · tea-shop”“跑完了 · tea-shop”“出错中断 · tea-shop”“卡住了 · tea-shop”。
- 正文：会话标题（没有标题时用“未命名会话”），再加一句补充：跑完的写“用时 3 分 20 秒”，卡住的写“已 15 分钟没有动静”。
- 来源写在正文末尾（Claude Code / Codex / Cursor）。
- 点击：在默认浏览器里打开 `http://127.0.0.1:<端口>/#/s/<会话 id>`。
- 通知里**不放**提示正文、工具参数、输出等对话内容：通知会显示在锁屏和通知中心里。

## 5. 结构

```
pipeline.onChanges ──> NotificationEngine（纯逻辑：状态 + 设置 + 时钟 → 要发的通知）
                              │
                              ▼
                        Notifier（投递接口）──> 系统桌面通知（按平台）
```

### 5.1 NotificationEngine

- 纯逻辑，不碰系统：输入是变更、当前时间、设置、“是否正在导入”；输出是要发的通知列表。时钟可注入，卡住检查由一个每 30 秒触发的定时器驱动（同样可注入）。
- 每个会话记：当前状态、这一段运行的开始时刻、每种通知上一次发出的时刻和对应的“那一次”。只在内存里；服务重启后从当前会话状态重新开始（重启后不补发重启前的事）。
- 会话被淘汰出内存或删除时，对应的记录一并丢掉。

### 5.2 Notifier（投递）

接口：`notify({ title, body, url }): Promise<void>`，失败时拒绝。一个实现：系统桌面通知，不引入新的依赖，按平台调用系统自带的命令：

| 平台 | 做法 |
|---|---|
| Windows | 用 PowerShell 调系统的 Toast 通知接口，点击时按协议打开网址 |
| macOS | `osascript` 的 `display notification`（系统限制：点击不能带网址，正文里附上网址） |
| Linux | `notify-send`（有的话）；点击行为取决于桌面环境 |

- 标题、正文、网址作为数据传入，不拼进命令行或脚本文本里执行（防止会话标题里的特殊字符被当成命令）。
- 每次投递有 5 秒超时；失败不重试，记下最近一次的错误和时间。同时在途的投递不超过 4 个，多出来的排队，队列超过 20 条时丢掉最旧的。
- 平台不支持或命令不存在：首次失败后标记为“不可用”，诊断页和设置里显示原因；之后每 10 分钟最多再试一次。

### 5.3 设置与接口

- 设置存在本机数据库的 `meta` 表（键 `notifications`），JSON。
- `GET /api/notifications/settings`：当前设置，加上投递状态（是否可用、最近一次错误和时间、最近一次成功的时间）。
- `PUT /api/notifications/settings`：整体替换设置；校验每个字段的类型和范围，不合法的返回 400。
- `POST /api/notifications/test`：立即发一条测试通知（不受总开关限制），返回成功或错误原因。
- 这三个接口和其余接口一样只接受来自本机的请求。

### 5.4 页面

- 顶栏“诊断”旁边加一个“通知”入口，打开设置面板：总开关、四个种类的开关、两个阈值、“发一条测试通知”按钮、投递状态（可用 / 不可用及原因）。
- 各来源能给出哪些通知（3.2 的表）以一句话的形式写在对应开关下面，例如“等你确认权限：需要装 hooks；Cursor 没有这个状态”。
- 诊断页加一行通知的状态：是否开启、最近一次发出的时间和种类、最近一次错误。

## 6. 错误处理

- 投递失败不影响采集和页面；错误只进诊断，不写进会话数据。
- 设置读不出来（损坏的 JSON）：按默认值（关闭）处理，并在诊断里说明。
- 引擎里的任何异常都被拦住并记录，不会让变更流的其他订阅者受影响。

## 7. 测试

- 引擎：用合成的变更序列和可控的时钟，覆盖第 3 节每条规则——四种时机各自触发；导入期间不触发；旧事件不触发；同一次不重复；30 秒限流；出错优先于跑完；最短时长和卡住阈值的边界；设置关掉的种类不触发。
- 投递：把“运行系统命令”这一步注入成假的，验证各平台生成的命令和参数、特殊字符（引号、换行、`$`、反引号、尖括号）不会改变命令的含义、超时、排队和丢弃、不可用后的重试间隔。
- 接口：设置的读写和校验、测试通知。
- 真机：在这台 Windows 上实际弹出一条通知，并确认点击能打开会话页面（由人确认）。
- 约束不变：测试不弹真实的系统通知，不读写真实的数据目录。

## 8. 里程碑

1. 引擎（纯逻辑）和设置存取。
2. 投递（三个平台）和接口。
3. 页面：设置面板和诊断。
4. 真机验证，更新 README 和使用手册。
